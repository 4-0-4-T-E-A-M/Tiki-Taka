### `POST /user/signup` — 유저 회원가입
- **담당자**: 미배정
- **마감일**: 2025-02-20
- **작업 설명**
    - 유저 회원가입
    - 사용자 역할 부여 (일반)
- **요청**
    - 유저네임
    - 패스워드

### `GET /user/booking` — 마이페이지 - 예매 내역 목록 확인
- **작업 설명**: 예매 내역 목록 확인
- **응답**
    - 공연 정보
        - 제목
        - 아티스트
        - 날짜
        - 공연 장소
        - 지역
        - 가격
        - 사진
        - 장르
    - 성공 여부
    - 예매한 좌석 수

### `GET /user/booking/{bookingId}` — 마이페이지 - 예매 내역 상세 확인
- **작업 설명**: 예매 내역 상세 확인
- **기본 정보**
    - 예매 시도 시각
    - 내 요청이 서버에 도착한 시각
    - 성공/실패 여부
    - 시도한 좌석 정보 (구역, 좌석 번호)
- **성공 시**
    - 최종 예매 확정 시각
    - 오픈 후 몇 초만에 성공했는가
    - 전체 성공자 중 몇 번째였는가 (순위)
- **실패 시**
    - 해당 좌석이 선점된 시각
    - 내 요청과의 시간 차이 (몇 ms / 몇 초 늦었는가)
    - 실패 시점 단계 (대기열 / 좌석 선택)
- **공통 맥락**
    - 해당 세션의 총 경쟁자 수
    - 좌석 매진 완료 시각
    - 성공자 평균 진입 시각

## 2. 공연

### `POST /performance` — 공연 등록 (관리자만)
- **작업 설명**
    - 공연 정보 등록 시 공연장 종류에 따라 좌석 배치도가 결정됨
        - *(실제로는 공연장마다 좌석 배치도가 다르지만, 한정된 좌석 배치도 내에서 연습)*
    - 공연장 종류에 따라 좌석 배치도 및 좌석 정보 자동 결정
        - 좌석 구역
        - 좌석 등급
            - R석: Royal / 최고급석
            - S석: Superior / 고급석
            - A석: A grade / A등급석
            - 이하 B, C석 다음 순
- **요청 (공연 정보)**
    - 제목
    - 아티스트
    - 날짜
    - 공연 장소
    - 지역
    - 공연장 종류
    - 가격
    - 사진
    - 장르

### `PUT /performance` — 공연 수정 (관리자만)

## 3. 티켓팅

### `POST /booking/setting` — 티켓팅 연습 정보 설정
- **작업 설명**
    - 티켓팅 API 스케줄러 예약
    - 사용자가 설정한 시각에 자동 실행되도록 함
        - 해당 시각에 티켓팅 API 호출 X (설정 시점엔 호출 안 함, 예약만)
- **요청**
    - 경쟁자 수 설정 (1 ~ 10,000명)
    - 시작 시각

### 서버 내부 함수 호출 (예정) — (서버 내부 API) 티켓팅
- **작업 설명**: 티켓팅 실제 서버와 동일하게 동작하도록 함
    - 좌석 선점은 봇이 해당 콘서트의 좋은 좌석(R > S > A ...)부터 우선 선점
    - 시작 시각에 맞춰 서버 오픈
    - 사용자가 선택한 경쟁자 수에 맞는 서버 부하 시도
    - 해당 서버 장애 시 처리 패턴 고려 필요 (NetFunnel 참고)
- ⚠️ 외부 노출 엔드포인트가 아니라 서버 내부 로직/함수로 설계 예정 (Path 미정)

### `POST /booking/start` — 티켓팅 시작 요청 (입장)
- **작업 설명**: 사용자가 설정한 시각에 맞춰 티켓팅 시작 버튼을 눌렀을 경우에 대한 요청 및 응답
    - 사용자를 대기열에 추가
    - 서버에 입장할 때까지 현재 순위를 보여준다 (SSE 방식)
- **요청**
    - 공연 ID
- **응답**
    - 현재 순위

### `GET/POST /booking/captcha` — 보안문자 띄워주기 / 입력
- **작업 설명**: 사용자가 처음 입장했을 때 보안 문자를 제대로 입력했는지 확인한다.
- **요청**
    - 사용자가 입력한 보안문자
- **응답**
    - 보안문자 일치 유무
- ⚠️ Notion 원본에서 GET(띄워주기)/POST(입력) 상세가 하나의 설명으로 통합되어 있어, 실제로는 아래처럼 나뉠 가능성이 높음 — 구현 시 확정 필요
    - `GET`: 캡차 이미지/문제 발급
    - `POST`: 사용자 입력값 검증 (위 요청/응답이 이쪽에 해당하는 것으로 추정)

### `GET /booking/section` — 구역 조회
- **작업 설명**: REST + 폴링 방식
    - 주기적으로 (5~10초) 서버에 좌석 상태 요청
- **요청**
    - 공연 ID
- **응답**
    - 구역 정보
        - 구역 ID
        - 구역 이름
        - 해당 구역의 남은 좌석
        - 해당 구역의 총 자리 수
        - 가격

```json
{
  "performanceId": 1,
  "title": "2024 아이유 콘서트",
  "sections": [
    { "sectionId": "A", "name": "VIP석", "total": 100, "remaining": 23,  "price": 165000 },
    { "sectionId": "B", "name": "R석",   "total": 200, "remaining": 0,   "price": 132000 },
    { "sectionId": "C", "name": "S석",   "total": 300, "remaining": 187, "price": 99000  }
  ]
}
```

### `GET /booking/section/{sectionId}` — 구역 내 좌석 조회
- **작업 설명**: 구역 내 좌석 조회
- **응답**
    - 구역 정보 (구역 ID, 구역 이름, 가격, 총 좌석 수, 남은 좌석 수)
    - 불가능한 좌석 정보 (좌석 ID, 좌석 상태)

```json
{
  "sectionId": "A",
  "name": "VIP석",
  "price": 165000,
  "total": 100,
  "remaining": 23,
  "unavailable": [
    { "seatId": 3,  "status": "BOOKED"   },
    { "seatId": 7,  "status": "ON_HOLD" },
    { "seatId": 15, "status": "BOOKED"   },
    { "seatId": 42, "status": "ON_HOLD" }
  ]
}
```

### `POST /booking/seat` — 좌석 선점
- **작업 설명**: 사용자가 좌석을 선택했을 경우
    - 사용자는 여러 좌석을 선택할 수 있다.
    - 좌석 선택 후 **확인**을 누르면 해당 좌석 상태에 따라 예매 가능
        - 선택한 자리 중 다른 사람이 이미 선택했으면 "이미 선택한 좌석입니다"
        - 성공 시 결제 창으로 이동: **7분간 홀딩**
    - 결제 창은 화면으로만 존재 (실제 결제 연동 없음)

**응답 - 성공 시** (좌석 ID, 구역 ID, 좌석 정보(행,열), 가격, 만료 시간)
```json
{
  "seatId": 5,
  "sectionId": "A",
  "row": "A",
  "col": 5,
  "price": 165000,
  "expiredAt": "2024-03-15T20:05:00"
}
```

**응답 - 실패 시** (좌석 상태: SEAT_UNAVAILABLE, 메세지, 현재 상태: ON_HOLD/BOOKED)
```json
{
  "code": "SEAT_UNAVAILABLE",
  "message": "이미 선택된 좌석입니다.",
  "currentStatus": "ON_HOLD"
}
```

- ⚠️ 요구사항 명세서(SC-04)에는 "5분 임시 선점"으로 되어 있으나, 이 API 상세 스펙(원본 Notion)에는 **7분**으로 적혀 있음 — 두 문서 간 불일치, 팀 확인 후 하나로 통일 필요

### `POST /booking/complete` — 결제완료 - 연습 결과 조회 및 좌석 상태 변경
- **작업 설명**
    - 결제 완료 시 해당 좌석을 BOOKED 상태로 바꾼다.
    - 해당 연습 로그를 보여줌
- **기본 정보**
    - 예매 시도 시각
    - 내 요청이 서버에 도착한 시각
    - 성공/실패 여부
    - 시도한 좌석 정보 (구역, 좌석 번호)
- **성공 시**
    - 최종 예매 확정 시각
    - 오픈 후 몇 초만에 성공했는가
    - 전체 성공자 중 몇 번째였는가 (순위)
- **실패 시**
    - 해당 좌석이 선점된 시각
    - 내 요청과의 시간 차이 (몇 ms / 몇 초 늦었는가)
    - 실패 시점 단계 (대기열 / 좌석 선택)
- **공통 맥락**
    - 해당 세션의 총 경쟁자 수
    - 좌석 매진 완료 시각
    - 성공자 평균 진입 시각

## 요구사항 명세서엔 있지만 이 API 문서엔 없는 항목 (팀 확인 필요)

아래는 `요구사항_명세서_및_디자인.pdf`의 기능 요구사항(U6, U8, U9, A3)에 명시되어 있지만, Notion API 명세서 테이블에는 엔드포인트가 없는 항목입니다. 추측으로 채우지 않고 목록만 표시합니다.

| 관련 요구사항 | 기능 | 비고 |
|---|---|---|
| U6 | 결제 (완료/실패 처리, 화면만) | `/booking/complete`가 이 역할을 겸하는 것으로 보이나 명시적 결제 API는 없음 |
| U8 | 예매 취소 / 환불 (토스페이먼츠 연동) | API 명세서에 없음 |
| U9 | 예매 알림 (Kafka → 이메일) | API 명세서에 없음 |
| A3 | 예매 현황 조회 (관리자, 매출 집계) | API 명세서에 없음 |
