# 공연 상세 조회 — 캐시 vs DB 응답속도 비교

Issue #53. 예매 흐름 초입에서 반드시 거치는 공연 상세 조회(`GET /api/performances/{id}` →
`PerformanceService.getPerformanceDetail()`)가 캐시 히트일 때와 캐시 미스(DB 직접 조회)일
때 응답 시간이 실제로 얼마나 차이 나는지 실측한 기록이다. sunwoo가 구현한 Cache-Aside
캐싱(#56)과 TTL·무효화 전략(#57)이 예매 도메인 관점에서 실제로 어떤 효과가 있는지 수치로
남긴다.

## 테스트 환경

- PostgreSQL 16 + Redis 7 (`docker compose up -d`, 로컬 1개 인스턴스, 같은 머신 — 네트워크
  왕복 지연은 반영되지 않음, 한계 항목 참고)
- 측정 대상: `PerformanceService.getPerformanceDetail(Long)` — 컨트롤러가 아니라 서비스
  메서드를 직접 호출해 측정했다. 이 API는 `SecurityConfig`에서 `anyRequest().authenticated()`로
  묶여 있어 HTTP로 직접 벤치마크하려면 매번 로그인이 필요한데, 인증 필터는 캐시 히트/미스
  양쪽에 동일하게 걸리는 비용이라 비교에 영향을 주지 않는다. 그래서 캐시-아사이드 로직 자체의
  응답 시간만 격리해서 쟀다.
- 캐시 TTL: `tikitaka.cache.performance-detail-ttl-ms` 기본값 15분(900,000ms) — 이번 측정과는
  무관(TTL 만료가 아니라 매번 명시적으로 `evictDetail`을 호출해 미스를 재현했다)
- 테스트 데이터: 회차 1개짜리 공연 1건(구역·좌석 없음) — 실제 인기 공연처럼 구역·좌석까지
  큰 공연은 DB 조회 비용이 이보다 클 수 있다(한계 항목 참고)

## 측정 방법

`src/test/java/.../performanceseat/service/PerformanceDetailCacheVsDbBenchmarkIT.java`
(평소엔 `@Disabled` — 로컬 docker compose가 떠 있을 때만 수동 실행)

1. 워밍업 5회(JIT·커넥션 풀 예열, 측정 제외)
2. **캐시 미스**: 매 호출 전 `evictDetail()`로 캐시를 비운 뒤 `getPerformanceDetail()` 호출 —
   순차 30회
3. **캐시 히트**: 캐시를 한 번 채운 뒤 `getPerformanceDetail()` 호출 — 순차 30회
4. **동시 요청**: 콘서트 오픈 순간 다수가 같은 공연 상세를 동시에 조회하는 상황을 재현 —
   `CountDownLatch`로 20개 스레드를 동시에 출발시켜 전체 소요 시간(wall time)을 측정.
   캐시를 비운 직후(cold, 스탬피드 상황)와 이미 채워진 상태(warm) 각각 1회씩

## 결과

| | 평균 | 최소 | 최대 | p95 |
| --- | --- | --- | --- | --- |
| 캐시 미스 (DB 직접, 순차 30회) | 6.871ms | 5ms | 16ms | 9ms |
| 캐시 히트 (Redis, 순차 30회) | 0.725ms | 0ms | 1ms | 1ms |

같은 조건에서 DB 직접 조회가 캐시 히트보다 평균 **약 9.5배** 느렸다(6.871ms vs 0.725ms).

| 동시 요청 20명 | 전체 소요 시간(wall time) |
| --- | --- |
| cache-cold (evict 직후, 스탬피드 상황) | 15ms |
| cache-warm | 3ms |

전체 원본 콘솔 출력:
```
[CACHE MISS (DB 직접, 순차 30회)] avg=6.871ms min=5ms max=16ms p95=9ms n=30
[CACHE HIT  (Redis, 순차 30회)] avg=0.725ms min=0ms max=1ms p95=1ms n=30
[CONCURRENT 20명 동시] cache-cold(evict 직후, 스탬피드 상황)=15ms  cache-warm=3ms
```

## 발견 1 — 절대 격차는 작지만 상대 격차는 뚜렷하다

로컬 환경(같은 머신, 네트워크 왕복 없음)이라 절대 시간 자체는 둘 다 한 자릿수 ms대로 작다.
하지만 **비율로 보면 DB 직접 조회가 캐시보다 일관되게 9배 이상 느리다** — `getPerformance()`
(공연 1건 SELECT) + `getSchedules()`(회차 목록 SELECT) 두 번의 쿼리와 JPA 엔티티 매핑을
거치는 경로와, Redis GET 한 번 + JSON 역직렬화만 거치는 경로의 구조적 차이다. 실제 서비스처럼
DB와 애플리케이션 서버 사이에 네트워크 홉이 있는 환경에서는 이 격차가 절대 시간 기준으로
더 벌어질 것으로 예상한다(측정하지 않음, 한계 항목 참고).

## 발견 2 — 스탬피드는 실제로 일어나지만, 이 규모에서는 체감되지 않는다

`PerformanceCacheRepository`는 캐시 스탬피드 대응(만료 직전 갱신, 분산 락 등)을 도입하지
않기로 결정한 상태다(#57 문서 참고, "PK 단건 SELECT라 DB 부담이 낮다"는 근거). 이번 측정으로
그 판단을 실측으로 뒷받침할 수 있었다.

`cache-cold` 20명 동시 요청의 전체 소요 시간은 15ms였다. 스탬피드 방지가 없으므로 20개
스레드 전부가 독립적으로 캐시 미스를 겪고 각자 DB를 조회했다는 뜻인데, 만약 이 20번의 DB
조회가 순차로 일어났다면 `6.871ms × 20 ≈ 137ms`가 걸렸어야 한다. 실제로는 15ms만 걸렸다는
건 20개의 조회가 커넥션 풀 위에서 충분히 병렬로 처리됐다는 뜻이다. 즉:

- **스탬피드(중복 DB 조회) 자체는 실제로 발생한다** — 20번의 캐시 미스가 각각 별도로 DB를
  때렸다.
- 하지만 조회가 PK 단건 SELECT 두 번으로 가볍고, 로컬 커넥션 풀이 20개 동시 요청을 감당할
  수 있어서, 이 규모(20명)에서는 체감 지연으로 이어지지 않았다.
- 이 결과는 "지금 트래픽 규모에서는 스탬피드 대응이 필요 없다"는 #57의 판단과 **일치한다**.
  다만 동시성이 수백~수천 단위로 커지거나(실제 콘서트 오픈 순간을 재현하는 이 프로젝트의
  목적을 생각하면 충분히 가능한 시나리오), 커넥션 풀이 포화되면 이 그래프가 어떻게 꺾이는지는
  이번 측정 범위 밖이다.

`cache-warm` 20명 동시 요청은 3ms로, 순차 히트 평균(0.725ms)의 약 4배였다 — Redis 단일
인스턴스가 20개 동시 GET을 처리하는 데 걸리는 자연스러운 오버헤드로 보이며, 여전히 매우
빠르다.

## 한계

- 로컬 1대 머신에서 한 세트만 측정했다. DB·Redis·애플리케이션이 모두 같은 머신에 있어
  실제 프로덕션의 네트워크 왕복 지연은 반영되지 않는다 — 실제 배포 환경에서는 캐시 히트와
  미스의 절대 격차가 이보다 클 가능성이 높다(테스트 예정, 이번 이슈 범위 아님).
- 테스트 데이터가 회차 1개짜리 단순한 공연이다. 구역·좌석까지 포함한 실제 규모의 공연
  상세를 캐시 미스로 조회할 때의 비용은 측정하지 않았다.
- 동시 요청은 20명, 1회만 측정했다. 반복 측정에 의한 평균/분산은 구하지 않았고, 수백~수천
  단위의 더 큰 동시성에서 커넥션 풀·DB 부하가 어떻게 변하는지는 확인하지 않았다.
- k6 기반 TPS 측정은 이번에 도입하지 않았다(로드맵상 k6는 아직 프로젝트에 세팅되어 있지
  않음) — 대신 애플리케이션 컨텍스트를 직접 띄운 통합 테스트로 서비스 레이어를 측정했다.
