# 문제 상황

대기열에 진입한 사용자는 자기 순번이 얼마나 남았는지 알아야 한다. 지금까지는 `GET /queue/me`를 클라이언트가 계속 다시 호출하는 폴링 방식으로만 확인할 수 있었는데, 이 방식은 순번이 안 바뀌어도 요청이 계속 나가고, 폴링 주기를 짧게 잡을수록 서버 부하만 늘어난다.

"서버가 순번 변화를 먼저 알려준다"는 요구사항만 놓고 보면 실시간 푸시라는 말에 WebSocket이 먼저 떠오르기 쉽다. 하지만 이 흐름을 자세히 보면 방향이 한쪽뿐이다.

> 서버 → 클라이언트로 "네 순번은 N번째다"를 계속 보내주기만 하면 되고, 클라이언트가 서버로 뭔가를 더 보낼 일이 없다.

이 단방향 요구사항 하나만 기준으로도 선택지가 갈리기 때문에, 왜 WebSocket이 아니라 SSE(Server-Sent Events)를 골랐는지, 그리고 이 프로젝트처럼 대량 동시 접속을 그대로 재현하는 목적을 가진 서비스에서 그 선택이 규모가 커져도 계속 유효한지를 실제 구현([SSE 대기열 순번 실시간 push 구현](https://github.com/4-0-4-T-E-A-M/Tiki-Taka/pull/61), 이슈 #54) 기준으로 정리한다.

# 고려한 대안 비교

| 방식 | 장점 | 단점 (이 프로젝트 기준) |
|---|---|---|
| 폴링 (기존 `GET /queue/me`) | 구현이 가장 단순. 상태 없는 일반 REST 요청이라 인프라 고려사항이 없음 | 순번이 안 바뀌어도 계속 요청이 나감. 폴링 주기를 촘촘히 잡을수록 대기자 수 × 주기만큼 불필요한 요청이 쌓임 |
| WebSocket | 양방향. 클라이언트→서버 메시지도 같은 연결로 보낼 수 있어 향후 좌석 선택처럼 상호작용이 필요한 기능에 재사용 가능 | 이번 요구사항(단방향)에는 기능이 과함. 별도 프로토콜 업그레이드(HTTP Upgrade)가 필요해 프록시·로드밸런서 호환성을 더 신경 써야 하고, 재연결·순번 복구 로직을 직접 구현해야 함 |
| SSE (최종 선택) | 표준 HTTP(1.1/2)만으로 동작해 인프라 호환성이 단순. 클라이언트 자동 재연결이 프로토콜에 내장(`EventSource`가 표준 동작으로 재시도). 서버 쪽은 `SseEmitter` 하나로 스트림을 열어두면 됨 | 서버 → 클라이언트 단방향만 가능. 브라우저가 도메인당 열 수 있는 동시 HTTP 연결 수에 제한이 있음(대략 6개 내외, HTTP/1.1 기준) |

# 최종 선택: SSE

순번 푸시는 정의상 단방향이다. WebSocket의 양방향성은 이번 요구사항에 쓰이지 않는 기능이고, 그 대가로 프로토콜 업그레이드 처리·재연결 로직 직접 구현 같은 복잡도만 추가로 떠안게 된다. SSE는 딱 필요한 만큼(단방향 스트림)만 제공하면서, 표준 HTTP 위에서 동작해 이 프로젝트가 이미 갖춘 인프라(Spring MVC, 일반 로드밸런서)를 그대로 쓸 수 있다는 점이 결정적이었다.

# 세부 설계 결정과 근거

SSE를 쓰기로 정한 뒤에도 "순번 변경을 어떻게 감지해서 커넥션에 push할지"는 별도로 풀어야 하는 문제였다(이슈 #54의 핵심 논의 지점). 여기서 내린 결정들이 지금 이 트레이드오프 문서가 근거로 삼는 실제 구현이다.

## 커넥션마다 스레드를 두지 않고, 단일 스케줄 태스크가 전체를 순회

`SseEmitterRegistry`에 열려 있는 커넥션 전체를 담아두고, `QueueRankBroadcaster` 하나가 `@Scheduled(fixedDelayString = queue.sse.poll-interval-ms)`(기본 1초)로 깨어나 그 전체를 훑는다. 커넥션 하나에 스레드 하나씩 붙이는 방식(이슈 #54가 제시한 첫 번째 대안)은 구현은 단순하지만 대기자가 수천 명이면 스레드 수도 그만큼 늘어나 이 프로젝트의 목적(대량 동시 접속 재현)과 정면으로 부딪힌다. 반대로 Redis Pub/Sub 기반 이벤트 팬아웃은 리소스 효율은 가장 좋지만 채널 설계와 "내 순번이 바뀌었는지" 판단 로직이 추가로 필요해, 이번 범위에서는 단일 스케줄 순회로 시작하고 병목이 실측되면 이벤트 기반으로 전환하는 단계적 접근을 택했다. (자세한 비교는 PR #61 설명 참고)

## 재조회 시 변경분만 전송

`QueueRankPusher`는 최초 연결 시(`force=true`)에만 무조건 전송하고, 이후 스케줄러가 반복 호출할 때(`force=false`)는 직전에 보낸 순번과 비교해 실제로 바뀐 경우에만 이벤트를 보낸다. 폴링을 없애려고 SSE로 바꿨는데 서버 내부적으로 다시 폴링(주기적 재조회)을 하는 구조이기 때문에, 적어도 "값이 안 바뀌었으면 클라이언트로는 아무것도 내려보내지 않는다"는 최소한의 절제는 지켰다.

## 재연결은 SSE 표준 동작에 맡기고, 순번 복구는 Redis가 진실 소스라 저절로 됨

SSE는 연결이 끊기면 브라우저의 `EventSource`가 자동으로 재연결을 시도하는 게 표준 동작이라, 서버가 별도의 재연결 프로토콜을 구현할 필요가 없다. 순번 자체는 애초에 커넥션이나 서버 메모리가 아니라 Redis ZSET(`WaitingQueueService`)에 저장돼 있으므로, 재연결되면 컨트롤러가 새 커넥션을 등록하고 최초 1회 push를 보내는 것만으로 끊기기 전 상태가 그대로 복구된다. WebSocket을 썼다면 이 재연결·상태 복구 로직을 직접 설계해야 했을 부분이다.

# WebSocket이 더 유리했을 조건

이 선택이 모든 상황에서 정답이라는 뜻은 아니다. 아래 조건 중 하나라도 현실화되면 WebSocket 전환을 검토해야 한다.

- **양방향 상호작용이 필요해지는 경우**: 예를 들어 "예매 페이지 진입 후 좌석 상태 실시간 갱신"처럼 클라이언트가 서버로도 뭔가를 계속 보내야 하는 기능이 추가되면, SSE로는 표현할 수 없고 별도의 요청 채널(추가 REST 호출)을 덧붙여야 해 WebSocket 하나로 처리하는 것보다 번거로워진다.
- **브라우저 동시 연결 수 제한이 실제로 문제가 되는 경우**: 브라우저는 HTTP/1.1 기준 도메인당 동시 연결 수를 6개 내외로 제한한다. 같은 화면에서 SSE 스트림 외에 일반 API 호출도 동시에 여러 개 나가야 하는 상황이라면 이 한도에 부딪힐 수 있다. (HTTP/2를 쓰면 이 제한은 사실상 사라지므로, 인프라가 HTTP/2를 지원하는지 여부가 이 조건의 실효성을 좌우한다.)

# 확장 시나리오에서도 이 선택이 유효한가

이 프로젝트의 존재 목적 자체가 "대량 동시 접속을 그대로 재현"하는 것이기 때문에, 대기자가 수천 명으로 늘어나거나 서버 인스턴스를 여러 대로 스케일아웃하는 상황을 짚고 넘어가야 한다.

- **동시 연결 수 관점**: SSE도 결국 커넥션 하나당 서버 자원(스레드는 아니지만 열린 연결·메모리)을 점유한다. 지금 구현은 커넥션 자체는 `SseEmitter` 하나(Servlet 비동기 처리라 스레드를 계속 점유하지는 않음)로 가볍지만, 재조회 스케줄러가 매 주기 전체 커넥션을 순회하는 비용은 커넥션 수에 비례해 늘어난다. WebSocket으로 바꿔도 이 "연결 수만큼 순회/브로드캐스트 비용이 는다"는 근본 성격은 동일해서, SSE 대신 WebSocket을 쓴다고 이 문제가 자동으로 풀리지는 않는다.
- **다중 인스턴스 스케일아웃 관점**: `SseEmitterRegistry`가 인메모리 `ConcurrentHashMap`이라, 서버 인스턴스를 여러 대로 늘리면 각 인스턴스는 자기에게 붙은 커넥션만 알고 있다. 만약 나중에 "특정 사용자의 순번이 바뀌었다"는 이벤트를 다른 인스턴스가 트리거하는 구조로 바뀌면(예: Redis 이벤트 기반 팬아웃으로 전환) 이 이벤트를 인스턴스 간에 전파할 방법이 별도로 필요해진다. 이건 SSE냐 WebSocket이냐의 문제가 아니라 "커넥션을 인스턴스 로컬 메모리에 들고 있다"는 설계의 한계이고, WebSocket으로 바꿔도 동일하게 겪는 문제다.

즉 SSE vs WebSocket 축에서는 여전히 SSE가 유리하지만(단방향인데 양방향 프로토콜을 쓸 이유가 없으므로), 규모 확장 문제는 SSE/WebSocket 어느 쪽을 택하든 "커넥션 순회 방식"과 "인스턴스 간 상태 공유" 설계로 별도로 풀어야 하는 문제다.

# 실측 결과

현재 갖고 있는 건 기능 동작 확인 수준이다. curl로 로컬에서 인증 없는 요청 401, 대기열 진입 후 순번 누적, SSE 연결 시 최초 push 즉시 수신, 순번 변화 없을 때 재전송 안 됨, 재연결 시 정상 복구까지는 확인했다(PR #61 참고). 다만 이건 대기자 1~2명 규모의 정성적 확인이고, 아래 항목은 **아직 측정하지 않았다 — 측정 예정**.

- 동시 SSE 연결 수백~수천 개 상황에서 `QueueRankBroadcaster`의 순회 1회당 소요 시간과 CPU 사용률
- 폴링 주기(`queue.sse.poll-interval-ms`, 현재 1000ms)를 늘리거나 줄였을 때의 리소스-지연시간 트레이드오프
- 같은 규모를 WebSocket으로 구현했을 때와의 정량적 리소스 비교 (지어내지 않음 — 아직 WebSocket 구현체 자체가 없어 비교 대상이 없다)

이 수치들은 k6 부하 테스트 도입 이후(`docs/ROADMAP.md` 기준 대기열 처리량 개선 주차) 채워 넣을 예정이다.

# 한계와 추후 과제

- **인메모리 레지스트리의 스케일아웃 한계**: 위 "확장 시나리오" 절에서 짚은 대로, 서버 인스턴스가 여러 대가 되면 `SseEmitterRegistry`는 인스턴스 로컬 상태로만 남는다. 지금 규모(로컬/단일 인스턴스 기준 연습 프로젝트)에서는 문제가 되지 않지만, 다중 인스턴스로 배포하게 되면 반드시 다시 검토해야 한다.
- **admitted(입장 허용) 이벤트 미구현**: 순번이 입장 허용 기준을 넘었을 때 알려주는 이벤트는 admitCount를 산정해줄 "공연 오픈 스케줄러"가 아직 없어 이번 범위에서 제외했다(5주차 이슈 소관). 이 문서가 다루는 SSE vs WebSocket 선택 자체에는 영향이 없지만, 대기열 기능이 아직 완결되지 않았다는 점은 밝혀둔다.
- **폴링 주기 1초가 실측 근거로 정해진 값이 아님**: 현재 `queue.sse.poll-interval-ms=1000`은 "일단 짧은 주기로 시작"한 값이라, 위 실측 결과가 나오기 전까지는 최적값이라고 볼 근거가 없다.

# 정리

이 프로젝트의 대기열 순번 푸시는 서버→클라이언트 단방향만 필요한 흐름이라, 양방향 프로토콜인 WebSocket의 장점(클라이언트→서버 메시지)을 쓸 일이 없다. SSE는 표준 HTTP 위에서 동작해 인프라 호환성이 단순하고 재연결이 프로토콜에 내장돼 있어, 딱 필요한 만큼의 기능으로 이번 요구사항에 정확히 맞았다. 다만 이 선택은 "지금 규모에서, 지금 요구사항 기준"이라는 전제가 붙는다 — 향후 좌석 상태 실시간 갱신처럼 양방향 상호작용이 필요해지거나, 서버를 여러 대로 스케일아웃하며 커넥션 상태를 인스턴스 간에 공유해야 하는 시점이 오면 이 판단을 다시 검토해야 한다. 그리고 그 재검토는 SSE를 WebSocket으로 바꾸는 문제라기보다, "커넥션을 어떻게 순회하고 인스턴스 간에 어떻게 공유할 것인가"라는 별개의 확장성 문제로 다뤄야 한다.
