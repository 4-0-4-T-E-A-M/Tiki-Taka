# 좌석 선점 동시성 제어: 분산 락(Redis/Redisson) 선택 이유

관련 이슈: #36

## 문제 상황

콘서트 티켓팅에서 동일 좌석에 대한 동시 요청은 "읽기 → 판단 → 쓰기"로 이어지는 임계구역(critical section)을 여러 요청이 동시에 통과하려는 경쟁 상태(Race Condition)를 만든다. 서버가 한 대라면 `synchronized`/`ReentrantLock` 같은 자바 기본 락으로 충분하지만, 트래픽 분산을 위해 서버(JVM)를 여러 대로 늘리는 순간 이 방식은 무력해진다. 각 서버의 로컬 락은 같은 JVM 메모리 안에서만 유효해서, A 서버가 락을 쥐고 있어도 B 서버는 그 사실을 알 방법이 없기 때문이다.

따라서 모든 서버가 공통으로 바라보는 외부 저장소를 이용한 **분산 락**이 필요하다.

- **분산 락**: 여러 서버에 걸쳐 상호 배제를 보장한다는 개념(패턴)이며 특정 기술의 이름이 아니다. Redis, ZooKeeper, DB 유니크 제약으로도 구현 가능하다.
- **Redis**: 분산 락을 구현할 수 있는 인프라(재료). `SET key value NX`가 원자적으로 처리되는 특성을 이용해 락을 흉내낼 수 있다. Redis 자체는 락이라는 개념을 알지 못한다.
- **Redisson**: Redis 위에서 락 소유자 검증, TTL 자동 연장(Watchdog), 재시도/대기 로직을 대신 처리해 `RLock` 객체 하나로 제공하는 자바 클라이언트 라이브러리. `tryLock(waitTime, leaseTime, unit)`처럼 `ReentrantLock`과 유사한 API를 제공해 학습 비용을 줄여준다.

## 비교 대상

- 방식 A: DB 유니크 제약 / 비관적 락(`SELECT ... FOR UPDATE`)
- 방식 B: ZooKeeper (znode 기반 큐 알고리즘, ZAB 프로토콜)
- 방식 C: Redis + Redisson 분산 락

## 각 방식 설명

### 방식 A — DB 유니크 제약 / `SELECT ... FOR UPDATE`
별도 인프라 없이 기존 PostgreSQL을 재활용할 수 있다. 다만 `INSERT`/`DELETE`·트랜잭션 자체가 디스크 I/O를 동반해 느리고, TTL 개념이 없어 자동 해제가 안 된다.

`SELECT ... FOR UPDATE`로 락을 잡으면, PostgreSQL은 `UPDATE`/`COMMIT` 시점에 WAL(Write-Ahead Log)을 먼저 디스크에 기록해 내구성(Durability)을 보장하는데, 이 디스크 쓰기가 메모리 접근보다 수백~수천 배 느리다. 게다가 락을 기다리는 요청은 DB 커넥션을 계속 붙잡고 블로킹되므로, 트래픽이 몰리면 커넥션 풀이 고갈되어 이 좌석과 무관한 다른 API 요청까지 지연되는 연쇄 장애로 번질 수 있다.

### 방식 B — ZooKeeper
znode를 순서대로 생성하고 "내 번호가 제일 작으면 내 차례"라는 큐 기반 알고리즘(ZAB 프로토콜)으로 매우 강한 정합성을 보장한다. 리더 선출처럼 절대 실수하면 안 되는 코디네이션에 적합하지만, 전용 클러스터 운영이 필요해 순수 락 용도로만 쓰기엔 운영 복잡도가 과하다.

### 방식 C — Redis + Redisson
인메모리 단일 스레드 순차 처리로 원자성이 보장되고 마이크로초 단위로 빠르다. TTL로 락이 자동 해제되며, Redisson이 락 소유자 검증·TTL 자동 연장·재시도 로직을 캡슐화해준다. 정합성 보장 수준은 ZooKeeper보다 이론적으로 약하지만(Redis 마스터 장애 시 극단적 예외 케이스 존재), 좌석 중복 예매 0건이라는 실용적 정합성 요구에는 충분하다.

## 트레이드오프 비교

| 항목 | DB 유니크 제약 (A) | ZooKeeper (B) | Redis + Redisson (C) |
|---|---|---|---|
| 속도 | 느림 (디스크 I/O) | 중간 (합의 과정) | 빠름 (인메모리) |
| 정합성 강도 | 중간 | 매우 강함 | 강함 (극단적 예외 존재) |
| 운영 복잡도 | 낮음 (기존 DB 재활용) | 높음 (전용 클러스터 필요) | 중간 |
| TTL 자동 해제 | 없음 | 있음 (세션 기반) | 있음 |
| 장애 시 자원 점유 | 대기 커넥션이 풀을 고갈시켜 연쇄 지연 유발 | 세션 기반이라 상대적으로 격리됨 | 실패 시 즉시 응답, 자원을 오래 붙잡지 않음 |

## 핵심 판단 기준

1. **속도가 요구사항 그 자체다.** 이 프로젝트는 트래픽 스파이크(다수의 동시 좌석 선점 요청)를 재현하는 것이 목적이므로, DB 유니크 제약이나 ZooKeeper의 오버헤드는 바로 병목으로 드러난다.
2. **정합성 요구 수준은 "충분히 강하면 됨"이다.** 은행 송금 수준(ZooKeeper급 강정합성)까지는 필요 없고, 좌석 중복 예매 0건을 실용적으로 보장하면 된다.
3. **이미 Redis를 캐싱·대기열(Sorted Set) 용도로 도입하기로 했다.** 락 하나만을 위해 별도 클러스터(ZooKeeper)를 새로 구축하는 것보다, 이미 도입한 Redis 한 대로 락·캐시·대기열을 함께 처리하는 편이 운영 부담이 훨씬 적다.

## 최종 선택 및 이유

**Redis(Redisson) 분산 락**을 선택한다.

- 여러 서버(JVM)에 걸쳐 "한 번에 하나만 통과"를 강제해야 하는데, 자바 기본 락(`synchronized`/`ReentrantLock`)은 한 서버 안에서만 유효해 부족하다.
- Redis는 인메모리 + 단일 스레드 순차 처리로 원자성이 보장되고, TTL로 자동 해제되며, 이미 캐싱·대기열 용도로 도입하기로 한 인프라라 운영 부담이 적다.
- Redisson은 락 소유자 검증, TTL 자동 연장, 재시도 로직을 직접 구현하지 않고 `RLock.tryLock(waitTime, leaseTime, unit)` 하나로 안전하게 쓸 수 있게 해준다.

### 락 + DB 트랜잭션은 함께 쓴다 (역할 분리)

락만으로는 부족하다. 좌석 하나를 예약 확정하려면 `seats`, `reservation_seats`, `reservations` 등 여러 테이블에 걸친 쓰기가 필요한데, 이 쓰기들이 트랜잭션으로 묶여 있지 않으면 중간에 서버가 죽었을 때(배포, 장애 등) 일부만 반영된 "유령 상태"가 남을 수 있다.

- **락 (Redis)**: 여러 요청이 동시에 몰릴 때 "누가 먼저 처리할 자격을 얻는가"를 정리한다.
- **트랜잭션 (DB, `BEGIN`~`COMMIT`)**: 그 한 명이 처리하는 여러 단계의 작업이 중간에 실패해도 반쪽짜리로 남지 않도록 원자적으로 보장한다.

락으로 "한 번에 한 명만 통과"하는 걸 보장해도, 통과한 사람이 하는 여러 단계 작업이 중간에 실패하는 건 락이 막아줄 수 있는 영역이 아니다. 두 메커니즘이 함께 있어야 "동시성 문제"와 "중간 실패로 인한 데이터 오염 문제"를 각각 해결할 수 있다.

### 락은 짧게, 5분 선점은 DB 상태값으로 표현한다

"좌석을 선택한 사람에게 5분간 우선권을 준다"는 요구사항 때문에 "5분짜리 락을 걸어두면 되는 것 아닌가"라는 접근이 자연스럽게 떠오르지만, 이는 채택하지 않는다.

- `unlock()`은 요청 처리 메서드가 리턴하는 순간(`finally`)에 실행된다. 진짜로 5분간 락을 유지하려면 요청을 처리하는 스레드가 5분 동안 리턴하지 않아야 하고, 그러면 사용자는 "좌석 선택 완료" 응답을 5분 뒤에나 받는다.
- 좌석을 선택한 사람 수만큼 서버 스레드가 5분씩 묶이므로, 트래픽이 몰릴수록 서버 자원을 더 빨리 고갈시켜 정작 막으려던 문제를 스스로 만든다.
- 결제 완료·취소·자동 만료도 결국 같은 좌석 행을 안전하게 바꿔야 하는 작업이다. 좌석 선택 시점에 5분짜리 락을 계속 쥐고 있으면, 결제 승인 콜백과 5분 만료 스케줄러가 거의 동시에 같은 좌석을 건드리는 경계 상황(예: 결제 승인 4분 59.9초, 만료 처리 5분 0.0초)에서 정합성을 지키기 위한 짧은 락 처리 자체가 막혀버린다.

대신 5분짜리 소유권을 락이 아니라 **DB 값**으로 표현한다: `reservation_seats.status = 'HOLDING'`, `hold_expires_at = NOW() + 5분`.

- 좌석 선택 요청이 끝나 락이 즉시 풀려도 이 값은 DB에 그대로 남는다.
- 다음 사람이 같은 좌석을 클릭하면 락을 잡을 필요 없이 `HOLDING` 상태 확인만으로 즉시 실패 응답을 줄 수 있다.
- 결제·취소·만료 각 이벤트는 발생 시점에 짧게 락을 걸고 상태를 안전하게 전이시킨다.

정리하면:
- **락**: "지금 이 순간 상태를 바꾸는" 짧은 트랜잭션 구간에서만 필요 (수백ms~수초)
- **HOLDING 상태 + 만료 시각**: 5분짜리 비즈니스 규칙을 표현하는 DB 값 (별도 락 없이 계속 유지)

`reservation_seats`의 상태 전이(`HOLDING → CONFIRMED`, `HOLDING → RELEASED`, `HOLDING → FAILED → PENDING_PAYMENT`)는 각 전이가 일어나는 순간마다 짧은 락 + 트랜잭션으로 처리하고, 그 사이의 "선점 유지" 자체는 DB 상태값이 담당하는 구조로 설계한다.
