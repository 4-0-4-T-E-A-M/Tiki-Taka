# 공연 상세 캐시 TTL·무효화 전략

관련 이슈: #57 (캐시 TTL·무효화 전략 결정), 전제: #56 (Cache-Aside 인기 공연 캐싱 구현)

# 문제 상황

이슈 #56에서 `PerformanceCacheRepository`가 공연 상세(`GET /api/performances/{id}`)를
공연 ID 단위로 Cache-Aside 캐싱하는 흐름을 만들었다. 이 시점의 TTL은 "캐시가 무한정 쌓이는
것만 막는" 플레이스홀더(5분)였고, 원본이 수정/삭제됐을 때 캐시를 어떻게 반영할지는 정해지지
않은 상태였다. 캐시를 실제로 운영하려면 다음 세 가지를 정해야 한다.

- TTL을 얼마로 잡을지
- 원본이 바뀌었을 때 캐시를 무효화할지, TTL 만료만 기다릴지
- TTL 만료 순간 다수 요청이 한꺼번에 DB로 몰리는 캐시 스탬피드에 대응할지

# 고려한 대안 비교

## TTL·무효화 조합

| 항목 | A. TTL만(무효화 없음) | B. 짧은 TTL + 무효화 없음 | C. 긴 TTL + 쓰기 시점 무효화 |
| --- | --- | --- | --- |
| 최신성 | TTL 길이만큼 항상 지연 | 지연이 짧음(수십 초~1분) | 수정 즉시 반영, TTL은 안전망 |
| 캐시 히트율 | TTL 길이에 비례 | 낮음 | 높음(변경이 드문 데이터 특성 활용) |
| 구현 복잡도 | 가장 단순 | 가장 단순 | `evictDetail` 호출 지점을 빠짐없이 챙겨야 함 |
| 이 프로젝트 데이터 특성과의 궁합 | "인기 공연은 오픈 전후로 거의 안 바뀐다"는 특성을 못 씀 | 특성을 못 쓰고 히트율만 희생 | 변경이 드물다는 특성 + 드문 변경은 무효화로 즉시 처리 |

`PerformanceService`가 이미 `updatePerformance`/`deletePerformance`라는 명확한 두 지점에서만
공연 상세를 바꾸기 때문에(공연/회차/구역/좌석을 서로 다른 애그리거트로 분리해 둔 도메인 규칙 —
`performanceseat/CLAUDE.md` 참고), 무효화 지점이 흩어져 누락되기 쉬운 구조가 아니다. C안의
단점(무효화 누락 위험)이 이 프로젝트에서는 상대적으로 작다고 판단했다.

## 캐시 스탬피드 대응 여부

| 항목 | 대응 안 함 | Refresh-ahead(만료 직전 비동기 갱신) |
| --- | --- | --- |
| 구현 비용 | 없음 | 스케줄러/락 등 추가 인프라 필요 |
| 이 캐시의 미스 비용 | PK 단건 `SELECT`(가벼움) | 낮은 비용을 낮추는 것 자체가 이득이 크지 않음 |
| 실제 경합 지점과의 관계 | 좌석 선점(진짜 경합)은 이미 별도 Redis 분산 락이 담당 | 상세 조회 캐시가 경합의 원인이 아님 |

# 최종 선택

## TTL: 15분, 설정값으로 분리

`PerformanceCacheRepository`의 TTL을 `application.yaml`의
`tikitaka.cache.performance-detail-ttl-ms`(기본값 900000ms = 15분, `PERFORMANCE_DETAIL_CACHE_TTL_MS`
환경 변수로 재정의 가능)에서 주입받도록 했다. "인기 공연 상세는 오픈 전후로 정보가 거의 안 바뀐다"는
이 프로젝트의 데이터 특성상, 무효화만 빠짐없이 챙긴다면 TTL을 짧게 가져갈 이유가 없다고 판단해
9주차 캐시 히트율 목표 쪽에 무게를 실었다. 하드코딩 대신 설정값으로 뺀 것은 실제 트래픽 패턴이
확인되기 전까지는 잠정치이기 때문이다 — 이슈 노트에서도 나중에 바뀔 가능성을 언급하고 있다.

## 무효화: 쓰기 시점 즉시 무효화(Write-side invalidation) 병행

`PerformanceService.updatePerformance`/`deletePerformance`가 각각 원본을 수정/삭제한 직후
`performanceCacheRepository.evictDetail(performanceId)`를 호출한다. 긴 TTL을 선택한 대신,
드물게 발생하는 변경은 TTL 만료를 기다리지 않고 즉시 반영해 "긴 TTL로 인한 최신성 저하"라는
단점을 상쇄한다.

## 캐시 스탬피드: 지금은 대응하지 않음

이 캐시가 미스됐을 때 발생하는 DB 조회는 `performanceId` 기준 PK 단건 `SELECT` 한 번이라
부담이 낮고, `docker-compose`/ROADMAP이 재현하려는 "실제 경합"은 좌석 선점(동일 좌석에 대한
동시 요청)이며 이는 이미 별도의 Redis 분산 락이 담당하도록 설계돼 있다(`docs/ROADMAP.md` 5주차
분산 락 통합). 공연 상세 캐시 미스가 다수 겹치더라도 "가벼운 SELECT가 잠깐 늘어나는" 수준이지,
이 프로젝트가 성능 지표로 삼는 좌석 선점 경로의 병목이 되지 않는다. 따라서 Refresh-ahead나 락
기반 스탬피드 방지를 지금 단계에서 도입할 필요가 없다고 결론 내렸다.

# 감수하는 단점과 한계

- **무효화 누락 위험** — 지금은 `updatePerformance`/`deletePerformance` 두 지점뿐이라 위험이
  작지만, 앞으로 공연 상세에 영향을 주는 쓰기 경로(예: 회차 상태를 별도 API로 변경하는 기능 등)가
  추가되면 그 경로에서도 `evictDetail` 호출을 빠뜨리지 않아야 한다. 새 쓰기 경로를 추가할 때는
  이 캐시에 영향이 있는지 항상 점검할 것.
- **캐시 스탬피드 판단은 현재 트래픽 규모를 전제로 한다** — k6로 실제 대량 동시 조회를 재현했을 때
  공연 상세 조회 자체가 병목으로 확인되면(9주차 캐시 히트율 측정 과정에서), 이 판단을 재검토해야
  한다.
- TTL 15분은 실측이 아니라 데이터 특성에 대한 추정에 근거한 잠정치다. 아래처럼 아직 벤치마크가
  없다.

# 실측 테스트 결과

TTL 값이 실제 캐시 히트율에 미치는 영향이나 캐시 스탬피드가 실제로 발생하는지에 대한 부하 테스트는
아직 수행하지 않았다 — 테스트 예정(9주차 캐시 히트율 측정 시 함께 확인). 현재는 Testcontainers
기반 통합 테스트(`PerformanceCacheRepositoryIT`)로 TTL이 저장 시점에 실제로 설정되는지, 무효화
후 캐시 미스로 전환되는지만 기능적으로 검증한 상태다.

# 정리

TTL과 무효화는 "최신성 vs 캐시 효율" 사이의 타협이다. 이 프로젝트는 캐싱 대상 데이터(공연 상세)가
자주 안 바뀌고, 변경 지점이 두 곳으로 명확히 좁혀져 있다는 조건 덕분에 "TTL은 길게, 무효화는
빠짐없이"라는 조합을 부담 없이 선택할 수 있었다. 캐시 스탬피드는 대응하지 않기로 했는데, 이 캐시의
미스 비용이 낮고 진짜 경합 지점(좌석 선점)이 이미 분리돼 있기 때문이다. 두 판단 모두 현재
트래픽 규모와 데이터 특성을 전제로 하므로, 9주차 캐시 히트율 실측 이후 TTL 값과 스탬피드 대응
필요 여부를 다시 검토한다.
