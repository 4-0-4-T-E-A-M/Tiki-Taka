
# 문제 상황

콘서트 티켓팅에서 가장 원초적인 요구사항은 이거다.

> 동일 좌석에 여러 명이 동시에 예매를 시도하면, 정확히 한 명만 성공하고 나머지는 즉시 실패해야 한다.

말은 간단하지만 "어느 레이어에서" 이걸 보장할지가 설계의 핵심 질문이었다. DB 트랜잭션만으로도 막을 수 있고, 애플리케이션 레이어에 락을 하나 더 둘 수도 있다. TikiTaka 프로젝트의 예매(Booking) 도메인을 맡으면서 이 결정을 내려야 했고, 그 과정에서 고려한 대안과 최종 선택, 그리고 실제로 부딪힌 문제를 기록해둔다.

# 고려한 대안 비교

| 방식 | 장점 | 단점 (이 프로젝트 기준) |
|---|---|---|
| DB 비관적 락<br>`SELECT ... FOR UPDATE` | 별도 인프라 없이 DB 트랜잭션만으로 해결 가능. 락이 트랜잭션 범위와 정확히 일치해 "커밋 전 락 해제" 같은 레이스가 애초에 없음 | 락 대기가 DB 커넥션을 점유 → 커넥션 풀이 곧 동시성 상한이 됨. 서버 인스턴스를 늘려도 결국 DB 커넥션이 병목. 즉시 실패시키려면 NOWAIT 등 별도 처리 필요 |
| DB 낙관적 락<br>버전 컬럼 | 정상 경로에서 락 대기 자체가 없어 처리량이 좋음. Seat 엔티티에 이미 `@Version` 필드가 있어 추가 구현 비용이 거의 없음 | 경합이 심할수록 OptimisticLockException 재시도 비용이 커짐. 재시도 횟수/대기시간을 애플리케이션이 직접 제어해야 하고, 100명이 동시에 부딪히면 대부분 재시도 루프를 도는 구조라 "즉시 실패 응답" 요구사항과 맞지 않음 |
| Redis 분산 락<br>Redisson (최종 선택) | 애플리케이션 레이어에서 즉시 성공/실패를 가를 수 있어 "대기 없이 즉시 실패" 요구사항에 정확히 맞음. DB 커넥션을 점유하지 않고 경합을 걸러내 DB 부하 자체를 줄임. 여러 서버 인스턴스로 확장해도(봇 트래픽 고려 시 필수) 분산 환경에서 동작 | 별도 인프라(Redis)가 추가됨. 단일 Redis 인스턴스 기준이라 Redis 장애 시 락 자체가 무력화됨 (Redlock 미적용) |

# 최종 선택: Redis 분산 락(1차) + DB 낙관적 락(2차)

Redis 분산 락 하나만 쓴 게 아니라, 기존에 이미 있던 Seat.version(낙관적 락) 위에 얹는 형태로 갔다.

- Redis 락이 같은 좌석에 대한 대부분의 경합을 애플리케이션 레벨에서 즉시 걸러준다.
- 혹시 락이 무력화되는 예외 상황(장애·버그)이 생겨도 **DB의 `@Version`**이 마지막 방어선 역할을 한다.

즉, "속도는 Redis, 최종 정합성 보증은 DB"로 역할을 나눈 조합이다.

# 세부 설계 결정과 근거

## 락 키 그레인: 좌석 단위 (`seat-lock:{seatId}`)

공연 단위가 아니라 좌석 단위로 잡았다. 세밀할수록 서로 다른 좌석을 노리는 요청끼리는 락 경합이 아예 안 생겨서 처리량이 좋아지는 대신, 좌석 수만큼 키가 늘어나는 트레이드오프가 있다. 이 프로젝트는 "같은 좌석을 향한 경쟁"이 핵심 시나리오라 세밀한 그레인을 선택했다.

## waitTime = 0 (즉시 실패)

대기열은 별도 도메인(Redis Sorted Set)이 담당하므로, 예매 서비스 레벨에서는 락을 못 잡으면 재시도나 대기 없이 바로 실패 응답을 준다. "락 획득 실패 = 이미 다른 사람이 선점"으로 취급한다.

## leaseTime = 3초

좌석 홀드의 5분 TTL(비즈니스 규칙)과는 다른 개념이다. 이건 임계 구역(좌석 조회 + 상태 전이 + DB 저장) 하나를 처리하는 동안만 락을 쥐고 있으면 되는 값이다. 정상 케이스면 수십~수백ms면 끝나기 때문에, GC나 순간적 지연을 흡수할 여유를 두고 3초로 잡았다. 너무 짧으면 처리 중에 락이 풀려버리고, 너무 길면 죽은 요청이 좌석을 오래 붙잡는 트레이드오프가 있다.

## 언락 타이밍

처음엔 단순히 finally에서 언락했다. 그런데 `@Transactional` 프록시의 실제 커밋은 메서드가 리턴된 이후에 일어난다는 걸 알게 되면서, "커밋 전에 락이 풀리는" 레이스가 있다는 걸 발견했다. 그 틈에 다음 스레드가 아직 커밋 안 된(겉보기엔 AVAILABLE인) 좌석을 잡을 수 있었다. 그래서 TransactionSynchronizationManager의 afterCompletion(커밋/롤백 이후)에 언락을 등록하도록 바꿨다. 이 부분이 실제로 겪은 문제라 가장 남겨둘 가치가 있는 포인트다.

# 실측 테스트 결과

ReservationConcurrencyTest에서 동시 예매 시나리오를 직접 돌려봤다.

- 동일 좌석에 100개 스레드가 CountDownLatch로 동시 출발 → 성공 1건 / 충돌(409) 99건, 그 외 형태의 실패 0건
- 테스트 종료 후 DB 최종 상태: 좌석 상태 HELD 1건, ReservationSeat 매핑 1건 — 정확히 의도한 상태로 수렴 확인

단, 이 수치는 로컬 단일 프로세스·단일 Redis 인스턴스 기준 결과다. 실제 다중 서버 인스턴스·k6 부하테스트 기준 수치는 아직 없고, 이후 부하 테스트 단계에서 확인할 예정이다.

# 한계와 추후 과제

정직하게 남겨둘 부분들이다.

- Redlock 미적용: 지금은 Redis 단일 인스턴스만 쓰고 있어서, 그 인스턴스가 죽으면 락 보장이 깨질 수 있다. 다중 Redis 인스턴스 기반 Redlock 알고리즘은 아직 도입하지 않았다. 이유는 연습 프로젝트 규모상 과설계로 판단했기 때문이다.
- 좌석 홀드 TTL 자동 만료 미구현: ReservationSeat.holdExpiresAt 필드는 존재하지만, 실제로 5분 지난 홀드를 AVAILABLE로 되돌리는 스케줄러/배치는 아직 없다. 다음에 할 일로 남겨둔다.

# 정리

DB 비관적 락은 커넥션 풀을 병목으로 만들고, 낙관적 락은 "즉시 실패"라는 요구사항과 맞지 않았다. Redis 분산 락을 1차 방어선으로, DB 버전 컬럼을 2차 방어선으로 두는 조합이 이 프로젝트의 목표(대기 없는 즉시 응답 + 분산 환경 확장성)에 가장 부합했다. 다만 Redis 단일 인스턴스 의존이라는 한계는 남아 있고, 이건 규모 대비 과설계 여부를 판단해 의도적으로 보류한 것이라는 점을 함께 밝혀둔다.
