# 인기 공연 랭킹 — Redis Sorted Set

관련 이슈: #94 (인기 공연 랭킹, 신선우)
참고: [[why-redis-lock]](#36) — Redis를 이미 락·대기열·캐시로 쓰고 있다는 전제

이 문서는 인기 공연 랭킹의 **점수 정책·키 구조·TTL·유실 대응**과, "왜 Redis Sorted Set인가
(vs DB 집계/배치 캐시)"를 정리한다.

# 1. 요구사항

- 홈 화면 "인기 공연 TOP N"을 빠르게 준다 — 매 요청마다 DB에서 `GROUP BY ... ORDER BY count`를
  돌리지 않는다.
- 순위는 **근사치면 충분**하다. "정확히 몇 번 조회됐나"가 아니라 "요즘 뜨는 공연"을 보여주는 게
  목적이다.
- 봇·새로고침 반복에 너무 휘둘리지 않고, 오래된 인기작이 영원히 상위에 고착되지 않는다.

# 2. 왜 Redis Sorted Set인가

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| **A. Redis Sorted Set (선택)** | `ZINCRBY` O(log N) 실시간 누적, `ZREVRANGE` O(log N + M) 상위 N, 이미 운영 중인 인프라 | 유실 시 정확한 값 복구 불가(근사치), TTL·버킷 관리 필요 | **채택** — 요구가 "근사 랭킹 + 빠른 조회"라 정확도 손실이 감당 가능 |
| B. DB 집계 쿼리 (매 요청) | 항상 정확, 별도 저장소 없음 | 인기 목록은 자주 조회되는데 매번 풀스캔/집계 → 오픈 시점 트래픽에 취약 | 조회 빈도가 높아 부적합 |
| C. DB 집계 + 배치 캐시 (N분마다 집계해 캐시) | 정확에 가깝고 조회는 캐시라 빠름 | 배치 주기만큼 지연, 집계 대상 이벤트 테이블(조회 로그 등)을 따로 쌓아야 함, 배치 인프라 | "조회 로그 테이블"을 새로 만들어야 하는 비용이 큼. 실시간성도 A보다 낮음 |

핵심은 **"인기도 원천 데이터를 어디에 쌓느냐"**다. C를 하려면 모든 조회를 DB row로 적재해야
하는데(쓰기 폭증), A는 `ZINCRBY` 한 번으로 끝난다. 정확도가 꼭 필요한 지표가 아니므로 A가 맞다.

# 3. 점수 정책

| 이벤트 | 가중치 (`application.yaml`) | 이유 |
| --- | --- | --- |
| 공연 상세 진입 | `view-weight` = 1.0 | 약한 신호. 봇·새로고침에 노출되므로 낮게 |
| 예매 확정(CONFIRMED) | `reservation-weight` = 10.0 | 강한 신호. "실제로 돈을 쓰는" 행동 |

- **조회수만 쓰지 않는 이유**: 이슈가 지적한 대로 봇·반복 요청에 취약하고, 조회는 많지만 아무도
  안 사는 공연이 상위에 남는다. 예매에 큰 가중치를 줘 "관심 → 전환"을 반영한다.
- 찜(위시리스트)은 이 프로젝트에 기능이 없어 제외. 생기면 가중치 하나 추가하면 된다.

# 4. 키 구조와 시간 감쇠

```
ranking:performance:score:{yyyyMMdd}     ← 일(day) 버킷. member=performanceId, score=그날 가중합
```

- **일 버킷**으로 나누는 이유: "오래된 인기작 고착" 방지. 조회 시 최근 `retention-days`(기본 7)일
  버킷을 **감쇠 가중치**로 합산한다 — 오늘 ×1.0, 어제 ×0.85, 그저께 ×0.85² ... (`decay-factor`).
  `ZUNION`(Redis 6.2+)으로 한 번에 계산하고 임시 키를 만들지 않는다.
- **TTL**: 각 버킷에 `retention-days + 1`일. 조회 윈도우 밖으로 나가면 자동 삭제 → 별도 정리 배치
  불필요. 경계에서 버킷이 먼저 만료되는 것을 막으려고 +1일 여유.
- 키 공간은 대기열(`queue:*`)·캐시(`performance:detail:*`)와 분리(`ranking:*`).

# 5. 엣지 케이스

| 상황 | 처리 |
| --- | --- |
| **동점** | Redis Sorted Set 규칙대로 member(`performanceId` 문자열) **사전순**. 합산 후 재정렬에서도 같은 규칙을 명시적으로 적용해 결과가 결정적이다 (`"10" < "2"` 같은 문자열 비교라는 점에 유의 — 안정적이면 충분) |
| **삭제/없는 공연** | 버킷에서 즉시 제거하지 않는다(버킷은 TTL로 사라짐). 조회 시 `limit × 3`을 뽑아 DB에 실제 존재하는 것만 남기고 순서를 유지, 앞에서 `limit`개 |
| **Redis 유실/초기화** | 재구축하지 않는다. `topPerformances`가 빈/부분 목록을 반환하고, 트래픽이 다시 버킷을 채운다. 근사 랭킹이므로 감수 |
| **점수 반영 중 Redis 장애** | `recordView`/`recordReservation`이 예외를 삼키고 로그만 남긴다 — 조회·예매 흐름을 절대 깨지 않는다 |
| **랭킹 조회 중 Redis 장애** | 빈 목록 반환 (홈 화면의 부가 요소라 200으로 degrade) |

# 6. 이벤트 연결

- **조회**: `PerformanceService.getPerformanceDetail`에서 캐시 히트 여부와 무관하게
  `recordView(performanceId)` 호출.
- **예매**: `reservation-events` Kafka 토픽의 별도 컨슈머 그룹(`popular-performance-ranking`)이
  `ReservationEvent`(status=CONFIRMED)를 받아 `scheduleId → performanceId`를 조회해
  `recordReservation`. 알림·통계 컨슈머와 독립(ROADMAP의 multi-consumer).
  - **주의**: 현재 booking 도메인이 `ReservationEvent` 프로듀서를 배선하지 않았다. 컨슈머는
    준비만 돼 있고, booking이 발행을 시작하면 자동 동작한다 — 그전까지 예매 가중치는 0이고
    랭킹은 조회수만으로 계산된다.

# 8. 실측 예정

- [ ] `ZUNION` 합산 지연 (버킷 7개, 공연 수 1만 기준)
- [ ] 조회 트래픽 하에서 `ZINCRBY` 부하가 대기열·락 Redis 사용과 경합하는지
- [ ] 감쇠 계수 0.85 / 윈도우 7일이 실제 "요즘 뜨는" 느낌을 주는지 (데이터 쌓인 뒤 튜닝)

# 9. 정리

→ 인기 랭킹은 **정확한 집계가 아니라 근사 순위**다. DB 집계는 조회 빈도 대비 비싸고, 배치 캐시는
   조회 로그 테이블을 새로 쌓아야 한다.
→ Redis Sorted Set + 일 버킷 + 시간 감쇠 + TTL 자동정리로 "빠른 조회 + 최근성 + 운영 부담 최소"를
   얻고, 정확도·유실 복구는 포기한다(요구가 그걸 허용).
→ 점수는 조회 1 : 예매 10. 삭제 공연은 조회 시 필터, Redis 유실은 무시하고 트래픽으로 재구축.
