# 대기열 설계 — Redis Sorted Set

관련 이슈: #118 (대기열 설계 트레이드오프 문서화, 신선우)
관련 구현: #49 (ZSET 순번), #54 (SSE 순번 push), #75 (공연 오픈 스케줄러), #102 (대기열 통과 처리),
#117 (스케줄러·대기열 동시성 안정성 테스트 — 이 문서의 "한계" 절이 다루는 문제를 실제로 고쳤다)
참고: [[sse-vs-websocket]](#54)

이 문서는 대기열의 **저장 구조·순번 발급 방식·입장 처리 방식·순번 전달 방식** 네 가지 결정을
대안과 비교하고, 3~4주차 구현 당시엔 알고 "7주차로 미룬다"고 적어뒀던 한계(ZPOPMIN+SADD 비원자성)가
#117에서 실제로 무엇을 깨뜨릴 수 있었는지와 어떻게 고쳤는지까지 정리한다.

# 1. 요구사항

- 연습 세션의 핵심은 "실제 티켓 오픈 순간의 경쟁"을 재현하는 것이다 — k6가 쏘는 봇 수백~수천 건이
  같은 회차에 거의 동시에 몰린다.
- 사용자는 "내가 몇 번째인지"를 실시간에 가깝게 알아야 하고, 서버는 그 순번대로 공정하게(새치기 없이)
  입장을 허용해야 한다.
- 대기열이 날아가면 연습 세션 자체가 무의미해지지만, 이 프로젝트는 실제 결제·정산이 걸린 서비스가
  아니므로 "영속성보다 속도"를 택할 여지가 있다 — 이 전제가 아래 1번 결정에 직접 영향을 준다.

# 2. 저장 구조: Redis Sorted Set

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| **A. Redis Sorted Set (선택)** | `ZRANK` O(log N) 순번 조회, `ZADD NX`로 중복 진입 방지가 자연스러움, `ZPOPMIN`으로 "앞에서부터 N명" 추출이 한 번에 됨 | 영속성이 약함 — Redis 재시작/장애 시 대기열 전체가 사라질 수 있음(AOF/RDB 설정에 의존) | **채택** — 요구사항 1번(공정한 순번 조회·추출)에 가장 직접적으로 맞는 자료구조이고, 유실 허용 범위(요구사항 3번)와도 맞음 |
| B. Redis List | 구현이 더 단순(`LPUSH`/`RPOP`) | "내 순번이 몇 번째인지" 조회가 O(N) — 리스트 중간 위치를 찾는 연산이 없음. 대기열의 핵심 기능(순번 표시)을 못 함 | 순번 조회 요구사항 자체를 못 채워 제외 |
| C. DB 테이블(순번 컬럼 + 조회) | 영속적, 장애 시 복구 가능, 트랜잭션 보장 | 대량 동시 진입(봇 수백~수천) 시 INSERT 경합이 그대로 DB에 부하로 전가됨 — 이 프로젝트가 재현하려는 바로 그 트래픽 패턴에 가장 취약한 선택 | 이 프로젝트의 목적(동시성 재현)과 정면 충돌해 제외 |
| D. Kafka 기반 대기열(토픽에 진입 이벤트 적재, 컨슈머가 순서대로 소비) | 순서 보장은 파티션 키로 쉽게 됨, 처리량 확장에 유리 | "내 현재 순번"처럼 임의 시점에 특정 사용자의 위치를 역조회하는 게 어려움(컨슈머 오프셋은 순번이 아님) — 별도 상태 저장소를 또 둬야 함 | 순번 조회라는 핵심 요구를 Kafka 혼자 못 풀어서 제외(결국 Redis/DB를 또 둬야 함) |

핵심 기준은 **"지금 내 순번이 몇 번째인지 빠르게 답할 수 있는가"**다. B·D는 이 질문에 답하려면
결국 별도 인덱스 구조를 더 둬야 하고, C는 이 프로젝트가 재현하려는 바로 그 동시 쓰기 트래픽에
가장 취약하다. A(Sorted Set)만 자료구조 자체가 질문에 바로 답한다.

# 3. 순번 score: INCR 원자 카운터 (vs 타임스탬프)

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 타임스탬프(`System.currentTimeMillis()`) | 추가 Redis 키 불필요, 구현 직관적 | 봇 수백~수천 건이 같은 밀리초에 도착하면 score가 충돌 — 동시 도착 순서가 뒤섞일 수 있음. 이 프로젝트는 "동시 다발적 봇 트래픽"을 그대로 재현하는 게 목적이라 이 충돌 조건이 실제로 발생한다 | 이 프로젝트 성격상 충돌이 드문 일이 아니라서 제외 |
| **`INCR` 원자 카운터 (선택)** | Redis `INCR`은 원자 연산이라 동시에 수천 개가 몰려도 중복 없는 순번을 보장 | 회차별 카운터 키(`queue:schedule:{id}:counter`)를 별도로 관리해야 함 | **채택** — `WaitingQueueRepository.addIfAbsent`에서 `increment(counterKey)` 뒤 그 값을 score로 `ZADD NX`. 카운터 관리 비용이 타임스탬프 충돌 위험보다 훨씬 작다 |

# 4. 입장 처리 방식: 주기적 배치 통과 (`admitFront`)

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| **A. 스케줄러 배치 입장 (선택)** | 구현이 단순(주기마다 "목표 - 이미 통과한 수"만큼 `ZPOPMIN`), 입장 허용 속도를 `admit-count` 하나로 통제 가능 | 폴링 간격(`queue.admission.poll-interval-ms`, 기본 1초)만큼 입장이 끊어서 일어남 — 실시간 1명 단위 입장은 아님 | **채택** — 끊어서 들어가는 지연이 사용자 경험에 치명적이지 않고(1초 단위), 구현·운영 복잡도가 가장 낮음 |
| B. 토큰 버킷/고정 비율 입장(초당 N명씩 연속 방출) | 입장이 더 매끄럽게(버스트 없이) 일어남 | 버킷 상태(토큰 수, 마지막 리필 시각)를 추가로 관리해야 하고, "오픈 즉시 초기 인원을 한꺼번에 들여보낸다" 같은 이 프로젝트의 요구(실제 티켓팅처럼 오픈 순간 몰리는 경쟁 재현)와는 오히려 안 맞음 | 이 프로젝트가 원하는 "오픈 즉시 몰리는 경쟁" 재현과 거리가 있어 제외 |
| C. 이벤트 기반(좌석 반납·결제 만료 등 이벤트가 발생할 때마다 그만큼만 입장) | 지연 없이 정확히 자리가 빈 만큼만 입장 | 이 프로젝트는 "입장 허용 인원(admit-count)" 자체가 좌석 수와 직접 연동돼 있지 않고 운영자가 정하는 값이라(초기값 100 등), 입장을 트리거할 "이벤트"가 명확하지 않음 — 좌석 반납 이벤트와 연동하려면 설계를 더 키워야 함 | 현재 범위(초기 admit-count만 있음)에서는 트리거할 이벤트가 불명확해 제외. ramp-up(점진적 증가, 7주차 Notes)이 도입되면 "ramp-up 틱"이 사실상 이벤트 역할을 대신한다 |

# 5. 순번 전달 방식: SSE push (vs 폴링)

이미 별도 문서([[sse-vs-websocket]](#54))에서 "서버→클라이언트 단방향이라 WebSocket 대신 SSE"를
결정한 근거를 다뤘다. 이 문서에서는 "폴링 대비 SSE를 왜 택했는가"만 한 문단으로 요약한다.

클라이언트가 `GET /queue/me`를 주기적으로 다시 호출하는 폴링은 구현이 가장 단순하지만, 순번이
안 바뀌어도 요청이 계속 나가 대기자 수 × 폴링 주기만큼 불필요한 부하가 쌓인다. 대량 동시 대기를
재현하는 이 프로젝트에서는 바로 이 "대기자 수에 비례하는 불필요한 요청"이 치명적이라, 서버가 변경
시점에만 밀어주는 SSE를 택했다 — 자세한 대안 비교·세부 설계(변경분만 전송, 재연결 처리 등)는
`sse-vs-websocket.md`를 참고.

# 6. 현재 구현의 한계와 대응

## (해결됨) ZPOPMIN + SADD 비원자성 → Lua 스크립트로 원자화 (#117)

3~4주차 구현 당시 `WaitingQueueRepository.admitFront`는 "대기열 앞에서 꺼내기(`ZPOPMIN`)"와
"통과 집합에 넣기(`SADD`)"를 애플리케이션에서 두 번의 Redis 호출로 나눠 했고, 코드 주석에
"원자적이지 않다 — 다중 인스턴스·프로세스 크래시 대응은 7주차"라고 명시적으로 미뤄뒀다.

#117에서 이 가정을 실제로 테스트했더니 두 가지 문제가 드러났다.

1. **크래시 유실**: `ZPOPMIN`이 성공한 직후, `SADD`를 호출하기 전에 프로세스가 죽으면 그 사용자는
   대기열에서는 빠졌지만 통과 집합에는 들어가지 못해 영구히 사라진다.
2. **목표 초과(overshoot)**: `WaitingQueueService.admitDueUsers`가 "목표(admit-count) 조회 →
   이미 통과한 수 조회 → 그 차이만큼 `admitFront` 호출"을 세 번의 별도 Redis 왕복으로 수행했다.
   다중 인스턴스가 같은 회차를 거의 동시에 처리하면 둘 다 "이미 통과한 수"를 같은 값으로 읽어
   같은 `slots`를 계산하고, 각자 그만큼씩 통과시켜 누적 통과 인원이 admit-count를 넘을 수 있었다.
   `WaitingQueueConcurrencyIT`(스레드 20개 동시 호출)로 이 overshoot을 재현해 확인했다.

두 문제 모두 "조회 → 계산 → 반영"을 애플리케이션 레벨에서 여러 Redis 왕복으로 쪼갰기 때문에
생긴다. 고친 방법은 전체를 Redis 서버 안에서 실행되는 **Lua 스크립트 하나로 묶는 것**이다 —
Redis는 스크립트 실행 중 다른 명령을 끼워넣지 않는 단일 스레드 실행 모델이라, 여러 인스턴스가
동시에 스크립트를 호출해도 Redis가 자동으로 직렬화해준다. 별도의 분산 락이나 CAS 재시도 로직 없이
"모두 실행해도 결과가 멱등"한 방식을 얻을 수 있어, 이 프로젝트 규모에 맞는 가장 저비용 해법이었다.

## (남음) 단일 Redis 장애 시 대기열 전체 영향

대기열(ZSET)·입장 허용 인원·통과 집합이 전부 같은 Redis 인스턴스에 있어, 이 Redis가 죽으면
해당 회차의 대기열 기능 전체가 멈춘다. 2번 표에서 이미 "영속성보다 속도"를 의식적으로 택했으므로,
지금 범위에서는 복제본(Replica)이나 AOF 영속성 설정으로 복구 가능성을 높이는 정도가 현실적인
대응이고, "대기열이 아예 안 날아가야 한다"는 요구가 생기면 그때 DB 백업 기록 같은 이중화를
추가로 검토해야 한다 — 지금은 이 요구가 없어 미룬다.

## (남음) 이탈한 사용자 정리

브라우저를 닫고 다시 안 돌아오는 사용자가 대기열 ZSET에 그대로 남아, 뒤에 있는 사용자의 순번
계산(앞사람 수)에 계속 끼어든다. TTL이나 하트비트 기반 정리가 없다 — 연습 세션은 보통 짧게
끝나는 데다(공연 오픈 직후 집중) 이탈자가 순번 "통과"에는 영향을 주지 않으므로(통과는 ZSET 앞에서
순서대로만 일어남) 당장 기능을 막는 문제는 아니지만, 세션이 길어지거나 재사용되는 시나리오가
생기면 정리 배치(예: 일정 시간 이상 순번 조회가 없는 엔트리를 제거)를 별도로 설계해야 한다.

# 7. 대안이 더 적합해지는 조건

- **대기열 데이터가 절대 유실되면 안 되는 요구가 생기면** → 저장 구조를 Redis Sorted Set 단독이
  아니라 DB와 이중 기록하거나(쓰기 비용 증가 감수), Redis AOF `always` 동기화로 바꿔야 한다.
- **좌석 반납·결제 만료처럼 "빈 자리가 생기는 이벤트"가 명확한 트리거로 자리잡으면** → 4번의
  이벤트 기반 입장 처리가 폴링 기반 배치보다 지연 없이 정확해져 더 유리해진다.
- **대기열 규모가 폭증해 조회(`ZRANK`)·추출(`ZPOPMIN`) 자체가 단일 Redis 인스턴스 CPU를
  병목으로 만들면** → 회차별 샤딩(현재도 회차 단위로 키가 분리돼 있어 샤딩 자체는 어렵지 않음)이나
  Redis Cluster 도입을 검토해야 한다.

# 8. 실측 결과

Testcontainers 기반 동시성 테스트로 "overshoot 없음", "오픈 반영 1회만" 수준)이고, 아래는

- [ ] 대기자 수천 명 규모에서 `admitUpToTarget`(Lua 스크립트) 1회 실행 지연
- [ ] 같은 규모에서 수정 전(비원자적 3-RTT 방식) 대비 처리량·지연 비교

- [ ] Redis 단일 인스턴스가 대기열 트래픽과 분산 락(`booking` 좌석 선점)·캐시 트래픽을 동시에
      받을 때의 상호 영향(현재는 모두 같은 Redis를 공유)

# 9. 정리

→ 저장 구조는 "순번을 빠르게 답할 수 있는가"가 기준이라 Sorted Set이 List·DB·Kafka보다
   명확히 유리하고, score는 동시 도착 충돌을 피하려 타임스탬프 대신 `INCR`을 쓴다.
→ 입장 처리는 토큰 버킷·이벤트 기반보다 단순한 주기적 배치(`admitFront`)를 택했다 — 이 프로젝트가
   재현하려는 "오픈 순간 몰리는 경쟁"과 운영 단순성에 더 맞기 때문.
