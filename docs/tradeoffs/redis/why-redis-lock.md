# 1. 락(Lock)이란 무엇인가

락은 한마디로 "이 구간은 한 번에 하나의 실행 흐름만 통과시킨다"는 약속을 코드로 강제하는 장치다.

왜 필요한지는 아주 단순한 예로 확인할 수 있다.

~~~java
private int count = 0;

public void increment() {
    count = count + 1; // 사실은 "읽기 → 더하기 → 쓰기" 3단계
}
~~~

스레드 A와 B가 동시에 increment()를 호출하면:

- A가 count를 읽는다 (0)
- B도 count를 읽는다 (0) — A가 아직 쓰기 전
- A가 1을 써넣는다 (count = 1)
- B도 1을 써넣는다 (count = 1)

두 번 호출했는데 결과는 1이다. 이게 경쟁 상태(Race Condition)이고, 콘서트 티켓팅에서 "10,000명이 같은 좌석을 동시에 누르는" 상황과 본질적으로 같은 문제다.

락은 이런 "읽고 → 판단하고 → 쓰는" 여러 단계를 하나의 묶음(임계구역, critical section)으로 만들고, 그 묶음 전체를 한 번에 하나의 흐름만 통과하게 강제하는 도구다.

# 2. synchronized/ReentrantLock으로는 왜 안 되는가

자바에는 이미 락 기능이 내장되어 있다.

~~~java
public synchronized void increment() {
    count = count + 1;
}
~~~

synchronized가 붙은 구간에는 한 번에 스레드 하나만 들어갈 수 있다. ReentrantLock도 원리는 같지만, tryLock(waitTime, ...)처럼 "얼마나 기다려볼지", "실패하면 어떻게 할지"를 세밀하게 컨트롤할 수 있다는 점이 다르다.

~~~java
private final ReentrantLock lock = new ReentrantLock();

public void increment() {
    if (lock.tryLock()) {
        try {
            count = count + 1;
        } finally {
            lock.unlock(); // 명시적으로 풀어줘야 함
        }
    }
}
~~~

문제는 이 락들이 관리하는 정보가 오직 같은 JVM(같은 프로세스) 메모리 안에서만 유효하다는 점이다.

~~~
서버 A (JVM 1)                     서버 B (JVM 2)
┌─────────────────────┐          ┌─────────────────────┐
│ synchronized로 잠금  │          │ synchronized로 잠금  │
│ → A 안에서는 안전    │          │ → B 안에서는 안전    │
└─────────────────────┘          └─────────────────────┘
        ↓                                 ↓
   같은 좌석에 동시에 접근하는데 서로의 락을 전혀 모름
~~~

서버가 한 대뿐이면 문제없지만, 트래픽 분산을 위해 서버를 여러 대로 늘리는 순간 이 방식은 무력해진다. A서버가 락을 쥐고 있어도 B서버는 그 사실을 알 방법이 없기 때문이다. 이 문제를 풀려면 모든 서버가 공통으로 바라보는 외부 저장소가 필요하다.

# 3. 분산 락, Redis, Redisson은 각각 다른 층위의 개념이다

여기서 세 단어가 자주 섞여 쓰이는데, 층위가 다르다.

~~~
분산 락        = 여러 서버에 걸쳐 상호 배제를 보장한다는 "개념"
Redis          = 그 개념을 구현할 수 있는 "인프라(재료)"
Redisson       = Redis 위에 분산 락을 편하게 쓸 수 있게 감싸놓은 "자바 라이브러리(도구)"
~~~

분산 락은 특정 기술의 이름이 아니라 패턴이다. (Redis, ZooKeeper, DB의 유니크 제약으로도 구현 가능)

Redis는 인메모리 키-값 저장소일 뿐이다. SET key value NX(키가 없을 때만 저장) 같은 명령이 원자적으로 처리되는 특성을 이용해 분산 락을 "흉내"낼 수 있는 재료가 된다. Redis 자체는 락이라는 개념을 알지 못한다.

Redisson은 그 재료로 락을 직접 구현할 때 필요한 번거로운 일들(락 소유자 검증, TTL 자동 연장(Watchdog), 재시도/대기 로직)을 대신 처리해서 RLock 객체 하나로 제공하는 자바 클라이언트 라이브러리다. tryLock(waitTime, leaseTime, unit)처럼 ReentrantLock과 똑같이 생긴 API를 제공해서, 로컬 락에서 분산 락으로 넘어갈 때 학습 비용을 줄여준다.

# 4. 왜 Redis인가 — DB 유니크 제약, ZooKeeper와 비교

분산 락을 구현하는 세 가지 방식을 비교하면 다음과 같다.

|  | DB 유니크 제약 | ZooKeeper | Redis(+Redisson) |
|---|---|---|---|
| 속도 | 느림 (디스크 I/O) | 중간 (합의 과정) | 빠름 (인메모리) |
| 정합성 강도 | 중간 | 매우 강함 | 강함 (극단적 예외 존재) |
| 운영 복잡도 | 낮음 (기존 DB 재활용) | 높음 (전용 클러스터 필요) | 중간 |
| TTL 자동 해제 | 없음 | 있음(세션 기반) | 있음 |

DB 유니크 제약은 별도 인프라가 필요 없다는 장점이 있지만, INSERT/DELETE가 디스크 I/O를 동반해 느리고 TTL 개념이 없다. 초당 수천 건이 몰리는 티켓팅 오픈 순간에는 DB 커넥션 풀 자체가 병목이 된다.

ZooKeeper는 znode를 순서대로 만들고 "내 번호가 제일 작으면 내 차례"라는 큐 기반 알고리즘(ZAB 프로토콜)으로 아주 강한 정합성을 보장한다. 리더 선출이나 절대 실수하면 안 되는 코디네이션에 적합하지만, 운영이 무겁고 순수 락 용도로만 쓰기엔 과하다.

Redis는 인메모리라 마이크로초 단위로 빠르고, TTL로 자동 해제가 되며, 구현도 Redisson이 대부분 캡슐화해준다. 정합성 보장 수준은 ZooKeeper보다 이론적으로 약하지만(Redis 마스터 장애 시 극단적 예외 케이스 존재), 좌석 중복 예매 0건이라는 실용적 수준의 정합성에는 충분하다.

콘서트 티켓팅 프로젝트에 Redis가 맞는 이유는 세 가지가 겹친다.

1. 속도가 요구사항 그 자체다. 트래픽 스파이크를 재현하는 게 프로젝트 목적인데, DB 유니크 제약이나 ZooKeeper의 오버헤드는 바로 병목으로 드러난다.
2. 정합성 요구 수준이 "충분히 강하면 됨"이다. 은행 송금 수준(ZooKeeper급)까지는 필요 없다.
3. 이미 Redis를 다른 용도(캐싱, 대기열)로도 쓰기로 했다. 락 하나만을 위해 별도 클러스터를 새로 구축하는 것보다, 이미 도입한 Redis 한 대로 락·캐시·대기열을 함께 처리하는 게 운영 부담이 훨씬 적다.

# 5. DB 락(SELECT FOR UPDATE)이 느린 이유

Redis 락과 DB 락을 비교할 때 "DB는 트랜잭션·디스크 I/O 오버헤드가 있다"는 말이 구체적으로 뭘 뜻하는지 짚어볼 필요가 있다.

~~~sql
BEGIN;
SELECT * FROM seats WHERE id = 1 FOR UPDATE;  -- 락 획득
UPDATE seats SET status = 'RESERVED' WHERE id = 1;
INSERT INTO orders (...) VALUES (...);
COMMIT;
~~~

Redis의 SET NX는 명령 하나로 끝나는 단발성 연산이지만, DB 트랜잭션은 BEGIN부터 COMMIT까지 여러 쿼리를 하나의 논리적 단위로 묶어 관리해야 해서 그 자체로 오버헤드가 있다.

더 결정적인 건 디스크 I/O다. PostgreSQL은 UPDATE나 COMMIT 시점에 변경 내역을 WAL(Write-Ahead Log)로 먼저 디스크에 기록한다. 이건 "서버가 중간에 죽어도 커밋된 데이터는 잃지 않는다"는 내구성(Durability)을 보장하기 위해서인데, 이 디스크 쓰기 자체가 메모리 접근보다 수백~수천 배 느리다.

여기에 락 대기의 연쇄 효과도 있다. A가 FOR UPDATE로 락을 잡고 있으면 B는 A가 커밋할 때까지 그 자리에서 블로킹되는데, 이 대기 시간 동안 B는 DB 커넥션 하나를 계속 붙잡고 있다. 10,000명이 몰리면 대기 커넥션이 쌓이면서 커넥션 풀 자체가 고갈되고, 이 좌석과 전혀 상관없는 다른 API 요청들까지 커넥션을 못 얻어 지연되는 연쇄 장애가 생길 수 있다. Redis 락은 실패하면 즉시 응답하고 자원을 오래 붙잡지 않기 때문에 이런 연쇄 병목이 훨씬 덜하다.

# 6. 락만으로는 부족하다 — DB 트랜잭션이 하는 일

좌석 하나를 예약 확정하려면 실제로는 여러 테이블에 걸친 쓰기가 필요하다.

~~~sql
UPDATE seats SET status = 'RESERVED' WHERE id = 123;
INSERT INTO reservation_seats (reservation_id, seat_id, status, hold_expires_at)
    VALUES (456, 123, 'HOLDING', NOW() + INTERVAL '5 minutes');
INSERT INTO reservations (user_id, status, ...) VALUES (789, 'PENDING_PAYMENT', ...);
~~~

이 세 줄이 트랜잭션으로 묶여 있지 않으면, 중간에 서버가 죽었을 때(배포, 장애 등) 일부만 반영된 "유령 상태"가 남을 수 있다. 예를 들어 seats 상태는 RESERVED로 바뀌었는데 reservations 행은 생성되지 못한 채 서버가 죽으면, 이 좌석은 누구도 취소할 수 없고 다른 사람도 예약할 수 없는 상태로 영구히 묶여버린다.

BEGIN~COMMIT으로 감싼 트랜잭션은 이 여러 단계를 원자적(atomic) 단위로 묶어, 전부 성공하거나 하나라도 실패하면 전부 롤백되도록 보장한다. 서버가 트랜잭션 도중 죽어도, 재시작 후 그 좌석은 마치 그 요청이 없었던 것처럼 원래 상태로 깨끗하게 돌아간다.

정리하면 락과 트랜잭션은 서로 다른 문제를 푼다.

- 락 (Redis): 여러 요청이 동시에 몰릴 때 "누가 먼저 처리할 자격을 얻는가"를 정리
- 트랜잭션 (DB): 그 한 명이 처리하는 여러 단계의 작업이 중간에 실패해도 반쪽짜리로 남지 않게 보장

락으로 "한 번에 한 명만 통과"하는 걸 보장해도, 통과한 사람이 하는 여러 단계 작업이 중간에 실패하는 건 락이 막아줄 수 있는 영역이 아니다. 그래서 락과 트랜잭션이 함께 있어야 "동시성 문제"와 "중간 실패로 인한 데이터 오염 문제"를 각각 해결할 수 있다.

# 7. 락은 짧게, 5분짜리 선점 상태는 DB에

가장 헷갈리기 쉬웠던 부분이 여기다.

"좌석을 선택한 사람에게 5분간 우선권을 준다"는 요구사항을 보면, "그럼 그 5분 동안 락을 계속 걸어두면 되는 거 아닌가?"라는 생각이 자연스럽게 든다. 하지만 이건 안 되는 이유가 명확하다.

락은 하나의 요청 처리 흐름(스레드)에 묶여 있는 개념이다.

~~~java
public void selectSeat(Long seatId) {
    RLock lock = redissonClient.getLock("seat-lock:" + seatId);
    lock.tryLock(0, 5, TimeUnit.MINUTES); // 5분 락?
    try {
        // HOLDING 처리
    } finally {
        lock.unlock(); // try 블록을 벗어나는 순간 즉시 풀림
    }
}
~~~

unlock()은 메서드가 리턴하는 순간(finally 블록) 실행된다. 진짜로 5분간 락을 유지하려면 이 요청을 처리하는 스레드가 5분 동안 리턴하지 않고 멈춰 있어야 하는데, 그러면 사용자는 "좌석 선택 완료"라는 응답을 5분 뒤에나 받게 된다. 서비스가 성립하지 않는다.

억지로 스레드를 5분씩 붙잡아두는 방식은 결국 좌석을 선택한 사람 수만큼 서버 스레드를 묶어두는 셈이라, 트래픽이 몰릴수록 서버 자원을 더 빨리 고갈시킨다 — 정작 막으려던 문제를 스스로 만드는 꼴이다.

더 중요한 문제는, 결제 완료·취소·자동 만료도 결국 같은 좌석 행을 안전하게 바꿔야 하는 작업이라는 점이다.

~~~
[좌석 선택]        락 획득 → HOLDING 기록 → 락 해제         (수백ms)
     ↓
[5분 대기 구간]     락 없음. HOLDING 상태 그 자체가 방어막    (최대 5분)
     ↓
[취소 or 만료 or 결제완료]  락 획득 → 상태 변경 → 락 해제    (수백ms)
~~~

만약 좌석 선택 시점에 5분짜리 락을 계속 쥐고 있다면, 결제 확정·취소·만료 처리가 모두 그 락이 풀릴 때까지 대기해야 한다. 특히 "결제 승인 콜백"과 "5분 만료 스케줄러"가 거의 동시에 같은 좌석을 건드리려는 경계 상황(예: 결제 승인이 4분 59.9초에 들어오고 만료 처리가 5분 0.0초에 도는 경우)에서는, 그 순간 짧게 락을 잡고 순서를 정해야 정합성이 지켜지는데 앞선 select가 락을 오래 쥐고 있으면 이 처리 자체가 막혀버린다.

해결책은 "5분짜리 소유권"을 락이 아니라 DB의 값으로 표현하는 것이다.

reservation_seats.status = 'HOLDING', hold_expires_at = NOW() + 5분 처럼 값으로 기록해두면:

- 좌석 선택 요청이 끝나도(=락이 즉시 풀려도) 그 값은 DB에 그대로 남아 있고
- 다음 사람이 같은 좌석을 클릭하면 락을 잡을 필요도 없이, HOLDING 상태를 확인하는 것만으로 즉시 실패 응답을 줄 수 있고
- 결제·취소·만료 각각의 이벤트는 그 발생 시점에 짧게 락을 걸고 상태를 안전하게 전이시키면 된다

정리하면:

- 락: "지금 이 순간 상태를 바꾸는" 짧은 트랜잭션 구간에서만 필요 (수백ms~수초)
- HOLDING 상태 + 만료 시각: 5분짜리 비즈니스 규칙을 표현하는 DB 값 (별도 락 없이 계속 유지)

우리 프로젝트의 reservation_seats 상태 전이(HOLDING → CONFIRMED, HOLDING → RELEASED, HOLDING → FAILED → PENDING_PAYMENT)도 각 전이가 일어나는 그 순간마다 짧은 락 + 트랜잭션으로 처리하고, 그 사이의 "선점 유지" 자체는 DB에 적힌 상태값이 담당하는 구조로 설계하면 된다.

# 8. 최종 정리

## 분산 락이 필요한 이유

→ 여러 서버(JVM)에 걸쳐 "한 번에 하나만 통과"를 강제하려면  
→ 자바 기본 락(synchronized/ReentrantLock)은 한 서버 안에서만 유효하므로 부족하다

## Redis를 선택한 이유

→ 인메모리 + 단일 스레드 순차 처리로 원자성이 보장되고, TTL로 자동 해제되며  
→ 이미 캐싱·대기열 용도로 도입하기로 한 인프라라 운영 부담이 적다

## Redisson을 쓰는 이유

→ 락 소유자 검증, TTL 자동 연장, 재시도 로직을 직접 구현하지 않고  
→ RLock.tryLock(waitTime, leaseTime, unit) 하나로 안전하게 쓸 수 있다

## 락 + DB 트랜잭션을 함께 쓰는 이유

→ 락은 "누가 먼저 처리하는가"의 동시성 문제를,  
→ 트랜잭션은 "처리 도중 실패해도 중간 상태로 남지 않는가"의 정합성 문제를 각각 해결한다

## 락을 짧게 유지해야 하는 이유

→ 5분짜리 좌석 선점은 락이 아니라 DB의 상태값(HOLDING + hold_expires_at)으로 표현하고  
→ 락은 그 값을 "바꾸는 순간"에만 짧게 걸어야, 결제/취소/만료 처리가 서로 막히지 않는다
