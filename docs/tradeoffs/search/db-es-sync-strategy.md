# 현재 상태 (코드 기준)

- Kafka 프로듀서·컨슈머 기본 구조는 이미 있다(#81) — `KafkaEventProducer`/`KafkaEventConsumer`/
  `KafkaTopics`. 다만 현재는 `RESERVATION_EVENTS` 토픽과 `ReservationEvent` 하나뿐이고 예매
  도메인 전용이다. 같은 패턴(토픽 상수 추가 + 전용 이벤트 record)을 공연 변경 이벤트에도 재사용할
  수 있다 — 즉 "Kafka를 쓸지 말지"가 아니라 이미 있는 Kafka 인프라를 검색 동기화에도 쓸지의
  문제다.
- `docker-compose.yml`에 Debezium/Kafka Connect 등 CDC 전용 인프라는 없다 — CDC를 선택하면
  새 인프라를 추가해야 한다.
- `Performance` 엔티티(`performanceseat/entity/Performance.java`)에 `updatedAt`/버전 컬럼이 없다
  — `createdAt`만 있고 수정 시각을 추적하지 않는다. 어떤 전략을 택하든 "이 이벤트가 최신
  상태인가"를 판단하려면 이 필드가 필요할 가능성이 높다(아래 순서 역전 대응 참고).
- 동기화 트리거 지점은 `PerformanceService`의 `createPerformance`/`updatePerformance`/
  `deletePerformance` 세 메서드뿐이다 — 좌석/회차/구역 변경은 검색 인덱스와 무관(검색 대상은
  공연 자체 필드).

# PostgreSQL과 Elasticsearch의 책임

- **PostgreSQL이 source of truth.** ES는 항상 PostgreSQL의 파생 뷰이며, ES가 유실되거나 꼬여도
  PostgreSQL 재조회로 항상 복구 가능해야 한다(전체 재색인으로 원상 복구).
- **동기화 대상 필드**: `title`, `artist`, `genre`, `region`, `venueName`, `posterUrl` — [[queryDSL-vs-es-role-split]](#86)의 책임표에서 ES가 담당하기로 한 자유 텍스트 검색·자동완성
  대상 필드와 목록에 표시할 필드만. `description`은 검색/자동완성 대상이 아니면 색인 제외 후보
  (#90에서 검색 품질 보고 결정). 좌석·가격·회차 데이터는 별도 애그리거트라 동기화 대상 아님.
- **동기화 단위는 공연(Performance) 전체 문서 upsert** — 필드별 부분 업데이트가 아니라 항상 공연
  하나를 통째로 다시 색인한다(아래 "이벤트에 페이로드를 싣지 않는" 설계와 연결).

# 후보 방식 비교

| 방식 | 장점 | 단점 | 이 프로젝트에서의 비용 |
| --- | --- | --- | --- |
| **A. 실시간 이벤트 (Kafka)** | 지연 낮음(초 단위), 기존 프로듀서·컨슈머 패턴(#81) 재사용 가능, 로드맵이 Kafka 활용을 원래 목표로 함 | 발행 실패/유실 시 드리프트 발생 가능, 컨슈머가 멱등적으로 짜여야 함 | 낮음 — 토픽 상수 1개, 이벤트 record 1개, 발행 호출 3곳만 추가 |
| **B. 주기 배치 재색인** | 구현 가장 단순, 실패해도 다음 주기에 항상 수렴(자가 치유) | 지연이 배치 주기만큼 큼(최대 N분), 데이터 규모 커지면 매번 전체 재색인 비용 증가 | 낮음 — `PerformanceRepository.findAll()`이 이미 있어 스케줄러만 추가하면 됨 |
| **C. Outbox 패턴** | DB 트랜잭션과 이벤트 발행이 원자적(dual write 문제 없음) | Outbox 테이블 + 폴러(relay) 신규 구축 필요, 컨슈머 멱등성은 여전히 필요 | 높음 — 이 프로젝트에 아직 outbox 인프라가 전혀 없음 |
| **D. CDC (Debezium 등)** | 애플리케이션 코드 변경 없이 WAL 기반으로 완전 결합 해제 | Kafka Connect/Debezium 커넥터 등 새 인프라, 운영 복잡도 가장 큼 | 매우 높음 — `docker-compose.yml`에 관련 서비스 전혀 없음, 12주 일정에 새 인프라 하나 더 얹는 셈 |

`How` 섹션(#89 이슈 본문)이 이미 지적한 대로 dual write(A를 단순 구현했을 때의 위험)는 원자성이
없다는 게 핵심 리스크다. 이를 outbox(C)나 CDC(D)로 완전히 없앨 수도 있지만, 이 프로젝트 규모(공연
등록/수정 빈도가 낮고, 검색 지연 허용치가 초~분 단위로도 충분한 연습용 플랫폼)에서는 그 정합성
이득 대비 인프라 비용이 과하다.

# 최종 선택: A(실시간 이벤트) + B(배치 재색인)를 안전망으로 병행

- **평상시**: `PerformanceService`의 create/update/delete에서 `PerformanceChangedEvent`를
  Kafka로 발행(A). #81의 `KafkaEventProducer` 패턴을 그대로 따라 새 토픽(`performance-events`
  제안)과 새 이벤트 타입만 추가한다.
- **이벤트 페이로드는 필드 값이 아니라 `performanceId` + `eventType`(`UPSERT`/`DELETE`)만 싣는다.**
  컨슈머는 `UPSERT`를 받으면 그 순간 PostgreSQL에서 해당 공연을 다시 조회해 ES 문서 전체를
  덮어쓴다. 이렇게 하면:
  - **중복 수신**: 같은 이벤트가 두 번 와도 동일한 최신 상태로 덮어쓸 뿐이라 멱등 — 별도 dedup
    로직 불필요.
  - **순서 역전**: 이벤트 A(수정1)보다 이벤트 B(수정2)가 먼저 도착해도, 둘 다 "그 시점의
    PostgreSQL 최신값"을 다시 읽으므로 최종 상태는 항상 PostgreSQL과 일치한다(이벤트 자체의
    순서는 결과에 영향 없음). 단, Kafka 파티션 키를 `performanceId`로 둬서 같은 공연에 대한
    이벤트는 어차피 같은 파티션에서 순서대로 처리되게 한다(불필요한 재조회 경합 최소화 목적,
    정합성을 위한 필수 조건은 아님).
  - **삭제는 예외**: `DELETE` 이벤트는 재조회할 대상이 이미 없으므로 `performanceId`만으로 ES
    문서를 바로 삭제한다.
- **안전망**: `PerformanceRepository.findAll()`로 PostgreSQL 전체를 ES에 다시 밀어넣는 배치
  재색인(B)을 주기 실행(예: 1일 1회, 정확한 주기는 데이터 규모 보고 #90에서 조정) + 장애 복구 시
  수동 트리거 가능하게 만든다. 이벤트 발행 실패(Kafka 다운, 발행 코드 예외 등)로 생긴 드리프트를
  이 배치가 항상 원상 복구한다 — outbox/CDC 없이도 "최종적으로는 항상 일치"를 보장하는 역할.
- **Outbox(C)·CDC(D)는 채택하지 않는다** — 이 프로젝트 트래픽 규모와 일정에서 A+B 조합으로 이미
  "이벤트 유실이 나도 하루 안에는 자동 복구된다"는 보장을 얻을 수 있어, 새 인프라를 추가할 이득이
  비용보다 크지 않다고 판단.

# 실패·중복·순서 역전·전체 재색인 대응 요약

| 상황 | 대응 |
| --- | --- |
| Kafka 발행 실패(DB 커밋 후 publish 예외) | 즉시 재시도는 하지 않음(dual write 원자성 어차피 없음) — 다음 배치 재색인(B)이 흡수 |
| 이벤트 중복 수신 | 컨슈머가 매번 PostgreSQL 재조회 후 upsert라 자연히 멱등 |
| 이벤트 순서 역전 | 재조회 방식이라 최종 상태에 영향 없음(파티션 키로 순서를 최대한 보장하되 필수는 아님) |
| ES 전체 유실/오염 | 배치 재색인(B) 수동 트리거로 `findAll()` 기준 전체 재구축 |
| 컨슈머 자체 장애(오래 다운) | 재가동 시 컨슈머 그룹 오프셋부터 밀린 이벤트 순차 처리 + 그 사이 배치가 이미 최신화했을 수 있어 중복 upsert만 발생(멱등하므로 무해) |
