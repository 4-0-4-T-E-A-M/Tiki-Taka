# 공연 검색에 Elasticsearch를 쓰는 이유

관련 이슈: #91 (★ ES 선택 이유 트레이드오프 문서화, 신선우)
전제:
- [[queryDSL-vs-es-role-split]] (#86) — "어떤 조회를 어느 저장소가 담당하는가"는 여기서 정했다.
  이 문서는 그중 **"공연명/아티스트 자유 텍스트 검색을 왜 하필 Elasticsearch로 하는가"**만 다룬다.
- [[db-es-sync-strategy]] (#89/#106) — DB→ES 동기화 방식. 이 문서는 "동기화 비용이 있다"는
  사실만 근거로 쓰고 구체 전략은 그 문서를 따른다.

이 문서가 다루지 않는 것:
- 구조화 필터(genre/region/날짜) 조회 → 이미 QueryDSL로 확정([[queryDSL-vs-es-role-split]]),
  ES 후보가 아님
- nori 매핑·인덱스 구현 세부 → #90 (`docs/infra/elasticsearch.md`)
- 인기순 랭킹 → #94 (Redis Sorted Set) — 검색 관련도가 아니라 카운터 랭킹이라 저장소 선택이 다름

# 1. 공연 검색이 실제로 해야 하는 일

홈 화면 검색창(`GET /api/performances/search?q=`)에 사용자가 기대하는 것:

| 기대 | 예시 |
| --- | --- |
| 아티스트/공연명 일부만 쳐도 나온다 | "아이유" → "2026 아이유 콘서트 : The Golden Hour" |
| 조사·띄어쓰기가 달라도 나온다 | "아이유의" / "아이유 " / "아이유콘서트" 모두 같은 결과 |
| 복합어의 일부로도 나온다 | "라이온" → "뮤지컬 라이온킹" |
| 검색어와 더 일치하는 게 위로 온다 | "콘서트" 검색 시 제목에 "콘서트"가 있는 게 공연장 이름에만 있는 것보다 위 |
| (선택) 타이핑 중 자동완성 | "아이" → "아이유", "아이브" 추천 |
| 장르/지역 필터와 함께 쓸 수 있다 | "페스티벌" + 지역=서울 |

핵심은 **"한국어 자연어를 형태소 단위로 이해해야 한다"**는 점이다. `LIKE '%아이유%'`는
"아이유"라는 **바이트 시퀀스**가 그대로 들어있는 행만 찾는다. "아이유콘서트"(붙여쓰기)나
오타는 못 찾고, 반대로 의미 없는 부분 매칭("아이유"가 우연히 포함된 다른 단어)도 걸러내지 못한다.

# 2. PostgreSQL만으로 이걸 하려면 — 후보 3가지

## A. `LIKE` / `ILIKE` (`title ILIKE '%kw%' OR artist ILIKE '%kw%'`)

가장 단순하다. QueryDSL로 이미 표현 가능하고 별도 인프라가 없다.

한계:
- **선행 와일드카드(`%kw`)는 B-tree 인덱스를 못 탄다.** 전체 테이블 Seq Scan이다.
  #72에서 `performances` 20,000행 규모에서 인덱스 없는 조건은 Seq Scan으로 처리됨을 실측 확인했다
  (그 이슈는 enum 필터 대상이었지만, 선행 와일드카드 LIKE는 정의상 인덱스를 못 쓰므로 동일하게
  Seq Scan이다).
- **형태소 분석이 없다.** "아이유콘서트"에서 "아이유"를 분리하지 못하고, "아이유의"는 "아이유"와
  다른 문자열로 취급한다. 띄어쓰기·조사 변형마다 사용자가 정확히 맞춰 입력해야 한다.
- 관련도 정렬·자동완성은 애초에 개념이 없다.

→ 이 프로젝트에서는 **ES 장애 시 폴백 경로**로만 쓴다(3절). 평상시 기본 경로로 쓰기엔 검색 품질이
   요구사항에 못 미친다.

## B. PostgreSQL 전문 검색 (`tsvector` / `to_tsquery`)

`to_tsvector('simple', title)` 같은 컬럼을 만들고 GIN 인덱스를 걸면 단어 단위 역색인 검색이 된다.
인덱스를 타므로 `LIKE`보다 빠르다.

한계:
- **기본 파서에 한국어 형태소 분석기가 없다.** `simple`/`english` 컨피그는 공백·구두점 기준
  토큰화만 한다. "아이유의 콘서트"는 `아이유의`, `콘서트` 두 토큰이 되고, `아이유`로는 안 잡힌다.
  조사가 분리되지 않는다.
- 한국어를 제대로 하려면 `textsearch_ko`, `mecab-ko` 등 **PostgreSQL용 형태소 분석 확장을 직접
  빌드·설치**해야 한다. 이건 ES에 nori 플러그인을 넣는 것과 운영 부담이 비슷하거나 더 크고
  (공식 지원이 약하고 PG 버전 업그레이드마다 재빌드), 그렇게 해도 관련도 스코어링·자동완성은
  ES만큼 성숙하지 않다.

## C. `pg_trgm` (트라이그램)

문자열을 3글자 조각으로 쪼개 유사도를 계산한다. `%` 연산자로 부분일치·오타 허용 검색이 되고
GIN 인덱스를 지원한다. "아이유콘서트"에서 "아이유"를 어느 정도 잡아낸다.

한계:
- **형태소가 아니라 글자 조각 기준**이라 한국어에서 정밀도가 떨어진다. 3글자 미만 검색어("아이")는
  거의 동작하지 않고, 의미 없는 부분 겹침(우연히 같은 3글자 조각을 공유하는 무관한 공연)이 섞인다.
- 인덱스 크기가 원문 대비 크게 늘어난다(모든 트라이그램을 색인).
- 관련도는 "트라이그램 겹침 비율"이라 "제목 일치 > 공연장 일치" 같은 필드 가중치를 주기 어렵다.
- 자동완성은 별도 구현 필요.

# 3. 후보 비교표

| 기준 | A. LIKE/ILIKE | B. PG 전문검색(tsvector) | C. pg_trgm | **D. Elasticsearch + nori** |
| --- | --- | --- | --- | --- |
| 한국어 형태소 분석 | ✗ 없음 | ✗ 기본 파서엔 없음 (확장 빌드 필요) | △ 글자조각 기반, 정밀도 낮음 | **✓ nori (조사 분리·복합어 분해)** |
| 조사·띄어쓰기 변형 대응 | ✗ | ✗ | △ | **✓** ("아이유의"→"아이유" 매칭, #90 IT로 검증) |
| 복합어 부분 검색 | ✗ | ✗ | △ | **✓** ("라이온"→"라이온킹", decompound=mixed, IT 검증) |
| 관련도(_score) 정렬 | ✗ | △ `ts_rank` (단어 빈도 기반) | △ 겹침 비율만 | **✓ 필드 가중치(title^2/artist^2)·BM25** |
| 자동완성 | ✗ | ✗ | ✗ | ✓ (edge-ngram/suggester — 이번 범위 아님, 확장 가능) |
| 복합 필터(genre/region) 결합 | ✓ SQL WHERE | ✓ | ✓ | ✓ (색인에 필드 포함, `bool.filter`) |
| 인덱스를 타는가 | ✗ (선행 와일드카드) | ✓ GIN | ✓ GIN (큼) | ✓ 역색인 |
| 별도 인프라 | 없음 | 없음(확장 설치 시 있음) | 없음(확장) | **있음 (ES 컨테이너)** |
| DB↔저장소 동기화 | 불필요 | 트리거/생성컬럼 | 트리거/생성컬럼 | **필요 (Kafka 이벤트 + 배치, #106)** |
| 장애 시 | DB와 운명 공동체 | 〃 | 〃 | **ES만 죽어도 PG 폴백 가능(#93)** |
| 운영 복잡도 | 최저 | 중(한국어 확장 시 상승) | 중 | **중~상 (컨테이너·동기화·장애대응)** |

# 4. 최종 선택: Elasticsearch + nori (키워드 검색 경로 한정)

**선택**: 공연명/아티스트 **자유 텍스트 검색**(`q` 파라미터가 있는 요청)의 **기본 경로**를
Elasticsearch(nori)로 한다.

**근거**:
1. **요구사항의 본질이 한국어 형태소 검색**이다(1절). 후보 A/B/C 중 이걸 제대로 하는 건 없거나
   (A, B 기본), 별도 확장을 빌드해야 하거나(B 한국어), 정밀도가 떨어진다(C). nori는 조사 분리와
   복합어 분해를 기본 제공하고, 이 프로젝트에서 실제로 동작함을 `PerformanceSearchIT`가
   재현 가능한 케이스로 검증한다("아이유의"→"아이유", "라이온"→"라이온킹").
2. **관련도 정렬(BM25 + 필드 가중치)**은 ES의 기본 기능이고 SQL 계열엔 대응 개념이 빈약하다.
3. **PostgreSQL에 한국어 형태소 확장을 넣는 비용**(비공식, PG 버전 업마다 재빌드)이 ES에 nori
   플러그인을 넣는 비용과 비슷하거나 크다. 이왕 형태소 분석 도구를 도입할 거면 검색 전용으로
   설계된 ES가 낫다.
4. **장애 격리**: ES가 죽어도 검색 API가 죽지 않는다. B/C는 PostgreSQL 위에 얹혀 있어 DB
   장애 = 검색 장애지만, ES는 별도 프로세스라 폴백 여지가 있다(3절이 아니라 아래 5절 참고 —
   실제 폴백은 #93에서 구현).

**적용 범위 (안 하는 것)**:
- 구조화 필터만 있는 조회(키워드 없이 genre/region/날짜만) → QueryDSL 그대로. ES 안 거침.
- 인기순 랭킹 → Redis(#94).
- 자동완성 → 이번 범위 아님(나중에 ES suggester로 확장 가능하다는 게 선택 이유 중 하나).

# 5. 감수하는 비용

## 인프라

- ES 컨테이너 1개 추가. `docker-compose.yml`에 `discovery.type=single-node`, 힙 512m로 제한
  (`docs/infra/elasticsearch.md`). PostgreSQL/Redis/Kafka와 함께 뜨므로 로컬 개발 머신
  메모리 부담이 늘어난다 — **실측 예정** (동시 부하 시 실제 힙 사용량은 측정 안 함).
- nori 플러그인 포함 커스텀 이미지 빌드(`docker/elasticsearch/Dockerfile`). 팀원이
  `docker compose up -d --build`를 한 번 돌려야 한다.

## 데이터 동기화 ([[db-es-sync-strategy]], #106)

- PostgreSQL이 source of truth, ES는 파생 뷰. 공연 CRUD 시 Kafka `performance-events`로
  변경 이벤트 발행 → 컨슈머가 PG 재조회 후 색인.
- **동기화 지연**이 존재한다: 이벤트 발행 → Kafka → 컨슈머 → ES refresh까지 수백ms~초 단위.
  이 사이 검색 결과가 PG와 잠깐 다를 수 있다 — 연습용 플랫폼이라 감수. **정확한 지연 분포는
  실측 예정**.
- 이벤트 유실 대비 매일 04시 전체 재색인(안전망). "최종적으로는 항상 일치"는 보장하되
  "항상 즉시 일치"는 보장하지 않는다.

## 장애 대응

- ES 다운 시 `PerformanceSearchService`가 예외를 잡아 PostgreSQL `ILIKE` 폴백으로 전환하고
  응답에 `degraded=true`를 실는다(#93 구현). 폴백 상태에서는 형태소 분석·관련도 정렬·자동완성이
  **빠지고** 단순 부분일치 + 최신순으로 축소된다. 페이지네이션·필터 계약은 동일하게 유지된다.
- `PerformanceSearchFallbackIT`가 이 동작을 엔드투엔드로 검증한다(ES 주소를 죽은 포트로 두고
  API 호출 → 200 + `degraded:true` + PG 결과).
- 즉 **ES는 "있으면 검색 품질이 좋아지는" 컴포넌트**이지, 없으면 서비스가 죽는 컴포넌트가
  아니도록 설계했다.

# 6. 선택하지 않은 대안이 더 적합해지는 조건

| 조건 | 그때 더 나은 선택 |
| --- | --- |
| 검색이 "정확히 일치하는 태그/코드 조회" 수준이고 자연어가 아니다 | A. `LIKE`/`=` (인프라 0) |
| 데이터 규모가 작고(수천 건) 검색 트래픽이 낮으며, 한국어를 "공백 기준 단어"로만 다뤄도 충분 | B. `tsvector` (인덱스는 타면서 인프라 추가 없음) |
| 오타 허용·부분일치가 핵심이고 형태소 정밀도는 덜 중요, ES 운영 인력이 없다 | C. `pg_trgm` |
| ES를 이미 다른 용도로 운영 중이라 한계 인프라 비용이 0에 가깝다 | D. ES (지금보다 더 확실한 선택) |
| 검색이 서비스의 핵심이고 자동완성·동의어·오타교정·다국어까지 필요 | D. ES (+ 사용자 사전·synonym·suggester 확장) |

이 프로젝트는 마지막 두 줄에 가깝다: "티켓팅 시뮬레이션"에서 공연을 찾는 경험이 자연스러워야
하고, 한국어 아티스트명·공연명 검색이 핵심 유스케이스이며, 확장(자동완성 등) 여지를 열어두고
싶다. 그래서 인프라·동기화 비용을 감수하고 ES를 택했다.

# 7. 실측 예정 (수치를 지어내지 않기 위해 명시)

- [ ] **검색 p95 응답시간**: 같은 데이터·쿼리로 ES vs PG `ILIKE` vs `pg_trgm` 비교. 20,000행 +
      대규모(수십만 행) 두 조건.
- [ ] **색인 지연 분포**: 공연 저장 → ES 검색 결과 반영까지 걸리는 시간(p50/p95).
- [ ] **ES 컨테이너 실제 메모리 사용량**: 동시 검색 부하 시 힙/RSS.
- [ ] **폴백 전환 시 응답시간·결과 차이**: ES 정상 대비 PG 폴백의 지연·결과 순서 변화.

측정 방법은 `PerformanceSearchIT`(nori 동작)·`PerformanceSearchFallbackIT`(폴백)와 동일한
Testcontainers 환경에 데이터 시더를 붙여 재현한다. 결과가 나오면 이 절을 수치로 채운다.

# 8. 정리

## 왜 ES인가

→ 공연 검색의 본질이 **한국어 형태소 검색 + 관련도 정렬**인데,
→ PostgreSQL `LIKE`는 형태소·인덱스 둘 다 안 되고, `tsvector`는 한국어 형태소에 별도 확장이
   필요하며, `pg_trgm`은 글자조각 기반이라 정밀도가 낮다.
→ nori는 이걸 기본 제공하고, 실제 동작을 재현 가능한 테스트로 검증했다.

## 감수하는 것

→ ES 컨테이너 + nori 이미지 빌드, Kafka 기반 동기화(지연 존재), 장애 대응 코드.
→ 대신 ES가 죽어도 PostgreSQL 폴백으로 검색 API는 살아있다(`degraded=true`).

## 적용 범위

→ 키워드(`q`) 검색만 ES. 구조화 필터는 QueryDSL, 인기 랭킹은 Redis.

## 아직 안 한 것

→ p95 응답시간·색인 지연·메모리 사용량은 **실측 예정**(7절). 자동완성·사용자 사전·동의어는
   확장 여지로 열어둠.
