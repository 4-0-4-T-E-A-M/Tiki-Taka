## Google OAuth 인증 도입 배경 및 설계 의도

### 1. 도입 배경

본 프로젝트의 핵심 목적은 회원가입, 비밀번호 관리, 계정 복구와 같은 유저 관리 시스템을 직접 구현하는 것이 아니다.

우리 서비스의 핵심은 사용자가 티켓팅 경쟁 시뮬레이션을 생성하고, 예매를 시도하며, 그 결과를 사용자별로 저장하고 조회할 수 있도록 하는 것이다.

즉, 인증 기능은 서비스의 핵심 도메인이 아니라, 사용자별 시뮬레이션 결과와 예매 결과를 안전하게 관리하기 위한 보조 수단에 가깝다.

따라서 자체 회원가입 및 로그인 시스템을 직접 구현하기보다, Google OAuth를 활용하여 인증 과정을 외부 인증 제공자에게 위임하는 방식을 선택하였다.

---

### 2. Google OAuth를 사용하는 이유

Google OAuth를 사용하면 사용자의 신원 확인 과정을 Google에 위임할 수 있다.

이를 통해 우리 서버는 비밀번호 저장, 비밀번호 암호화, 비밀번호 재설정, 이메일 인증, 계정 복구와 같은 복잡한 유저 관리 기능을 직접 구현하지 않아도 된다.

그 결과 인증 기능 구현에 드는 비용과 시간을 줄이고, 서비스의 핵심 기능인 티켓팅 경쟁 시뮬레이션, 예매 처리, 결과 저장 및 조회 기능에 더 집중할 수 있다.

또한 사용자는 별도의 회원가입 절차 없이 Google 계정으로 빠르게 로그인할 수 있으므로, 서비스 진입 장벽을 낮출 수 있다.

---

### 3. 인증 책임 분리

Google OAuth는 사용자가 실제 Google 계정의 소유자인지 확인하는 역할을 담당한다.

하지만 Google OAuth가 우리 서비스 내부의 사용자 권한까지 판단해주는 것은 아니다.

예를 들어 다음과 같은 판단은 우리 서버가 직접 처리해야 한다.

```
이 사용자가 우리 서비스의 몇 번 user_id인가?
이 사용자가 생성한 시뮬레이션은 무엇인가?
이 사용자가 조회하려는 예매 결과가 본인의 것인가?
이 결제 내역이 현재 사용자의 예매와 연결되어 있는가?
```

따라서 Google OAuth는 사용자 신원 확인에 사용하고, 우리 서버는 Google로부터 전달받은 사용자 정보를 내부 `users` 테이블의 사용자와 매핑한다.

이후 우리 서버는 자체 JWT를 발급하여 API 요청마다 사용자를 식별한다.

---

### 4. 전체 인증 흐름

Google OAuth 기반 인증 흐름은 다음과 같다.

```
1. 사용자가 Google 로그인 버튼을 클릭한다.

2. Spring Security OAuth2 Login을 통해 Google 로그인 페이지로 이동한다.

3. 사용자가 Google 계정으로 로그인한다.

4. Google은 인증된 사용자 정보를 우리 서버에 전달한다.

5. 우리 서버는 전달받은 이메일, 이름, provider id를 기준으로 users 테이블에서 사용자를 조회한다.

6. 기존 사용자가 없으면 users 테이블에 새 사용자를 생성한다.

7. 사용자 매핑이 완료되면 우리 서버는 자체 JWT를 발급한다.

8. 프론트엔드는 발급받은 JWT를 저장한다.

9. 이후 API 요청마다 Authorization 헤더에 JWT를 포함하여 요청한다.

10. 서버는 JWT를 검증하고, 토큰에 포함된 user_id를 기준으로 사용자를 식별한다.
```

---

### 5. 우리 서버 JWT를 별도로 발급하는 이유

Google OAuth를 통해 로그인에 성공하더라도, Google에서 발급한 토큰을 우리 서비스의 API 인증 수단으로 그대로 사용하지 않는다.

Google 토큰은 Google이 사용자의 신원을 확인했다는 증명에 가깝다.

반면 우리 서비스에서는 사용자를 내부 `user_id` 기준으로 식별해야 한다.

따라서 우리 서버는 Google 인증 결과를 바탕으로 내부 사용자를 찾거나 생성한 뒤, 해당 사용자의 `user_id`를 포함한 자체 JWT를 발급한다.

이를 통해 이후 API 요청에서는 Google 계정 정보가 아니라, 우리 서비스의 `user_id`를 기준으로 시뮬레이션, 예매, 결제 데이터를 처리할 수 있다.

---

### 6. 서비스 데이터와 사용자 식별

우리 서비스에서는 사용자가 생성한 시뮬레이션, 예매 결과, 결제 정보가 모두 사용자와 연결되어야 한다.

특히 시뮬레이션과 예매는 사용자 개인 데이터에 해당하므로, 로그인한 사용자만 생성 및 조회할 수 있어야 한다.

따라서 인증된 사용자를 내부 `users` 테이블의 `user_id`와 매핑하고, 해당 `user_id`를 기준으로 서비스 데이터를 저장한다.

예를 들어 사용자가 시뮬레이션을 생성하면 해당 시뮬레이션은 현재 로그인한 사용자의 `user_id`와 연결된다.

예매를 시도하는 경우에도 예매 데이터는 현재 로그인한 사용자의 `user_id`와 연결된다.

결제 데이터는 예매 데이터를 통해 사용자와 간접적으로 연결된다.

---

### 7. Security 계층과 Service 계층의 역할

본 프로젝트에서는 인증과 데이터 접근 권한 검증을 분리한다.

Spring Security는 요청이 컨트롤러에 도달하기 전에 로그인 여부와 JWT 유효성을 검증한다.

즉, 로그인하지 않은 사용자가 시뮬레이션 생성, 예매 요청, 결제 요청과 같은 보호된 API에 접근하면 SecurityFilterChain 단계에서 차단된다.

하지만 SecurityFilterChain을 통과했다는 것은 단순히 “로그인한 사용자”라는 의미일 뿐, 해당 사용자가 요청한 데이터의 소유자라는 의미는 아니다.

따라서 특정 시뮬레이션, 예매, 결제 내역을 조회할 때는 Service 계층에서 현재 로그인한 사용자의 `user_id`와 실제 데이터의 소유자 `user_id`를 비교해야 한다.

즉, 역할은 다음과 같이 분리된다.

```
Security 계층
= 로그인 여부와 JWT 유효성 검증

Service 계층
= 해당 데이터가 현재 로그인한 사용자의 것인지 검증
```

### 8. 기대 효과

Google OAuth를 도입함으로써 다음과 같은 이점을 얻을 수 있다.

```
1. 자체 회원가입 및 비밀번호 관리 구현 부담 감소

2. 빠른 로그인 기능 구현 가능

3. 사용자 입장에서 간편한 로그인 경험 제공

4. 인증 로직보다 핵심 도메인 개발에 집중 가능

5. Google 인증 결과를 내부 user_id와 연결하여 사용자별 데이터 관리 가능

6. JWT 기반 인증 구조를 통해 API 요청마다 일관된 사용자 식별 가능

7. Service 계층에서 데이터 소유권 검증을 수행하여 개인 데이터 접근 제어 가능
```

---

### 9. 최종 정리

본 프로젝트에서 Google OAuth를 사용하는 이유는 유저 관리 시스템 자체가 프로젝트의 핵심 목적이 아니기 때문이다.

우리 서비스의 핵심은 티켓팅 경쟁 시뮬레이션을 생성하고, 예매를 시도하며, 그 결과를 사용자별로 저장하고 조회하는 것이다.

따라서 사용자 인증은 Google OAuth에 위임하고, 우리 서버는 인증된 사용자를 내부 `users` 테이블의 사용자와 매핑한다.

이후 자체 JWT를 발급하여 API 요청마다 사용자를 식별하고, 시뮬레이션·예매·결제 데이터를 사용자별로 연결한다.

결론적으로 Google OAuth는 인증 구현 부담을 줄이고 빠르게 안정적인 로그인 흐름을 구축하기 위한 선택이며, 우리 서버는 OAuth 인증 결과를 기반으로 서비스에 필요한 사용자 식별과 데이터 소유권 검증을 수행한다.
