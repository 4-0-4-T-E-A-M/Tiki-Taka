# JWT와 Session 선택의 트레이드오프

## 1. 결정 요약

Tiki-Taka는 일반 요청에서 Access Token의 서명과 만료 시간, 그리고 토큰에 포함된 `userId`와 `role`을 검증하는 JWT 방식을 사용한다. 인증 필터가 매 요청마다 사용자 DB나 Redis를 조회하지 않도록 하여, 대규모 동시 예매 상황에서 인증 비용이 좌석 락·예약 트랜잭션·DB 커넥션 성능에 섞이지 않게 하는 것이 선택의 핵심 이유다.

이 선택은 JWT가 Session보다 항상 우수해서가 아니다. JWT는 매 요청 외부 저장소 조회를 줄이는 대신, 이미 발급된 Access Token의 권한과 유효성을 서버가 즉시 회수하기 어렵다는 단점을 가진다.

다만 현재 프로젝트의 ADMIN 사용자는 불특정 다수의 운영자가 아니라 프로젝트를 직접 운영하는 팀원 3명을 중심으로 구성된다. 관리자 계정 수와 사용 범위가 제한적이고, 현재 범위에서는 대규모 관리자 권한 회수나 관리자 강제 로그아웃 요구도 높지 않다. 따라서 Access Token의 최대 만료 시간만큼 권한 변경이 지연될 수 있는 위험은 존재하지만, 현재의 운영 범위와 신뢰 경계 안에서는 수용 가능한 수준으로 판단했다.

## 2. 현재 요구사항

현재 프로젝트에서 우선순위가 높은 요구사항은 다음과 같다.

- 대량 동시 예매 처리
- Redis 분산 락 경합 측정
- DB 커넥션 및 트랜잭션 부하 측정
- TPS, p95·p99 응답 시간 측정
- 인증 부하와 예매 부하의 구분
- 다중 서버 환경에서의 단순한 요청 검증

반면 현재 범위에서 상대적으로 우선순위가 낮은 요구사항은 다음과 같다.

- 관리자의 강제 로그아웃
- 대규모 관리자 권한 회수
- 관리자 role 변경의 실시간 반영
- 다수 운영자의 로그인 기기 관리
- 특정 Access Token의 즉시 폐기

여기서 우선순위가 낮다는 것은 해당 기능이 불필요하거나 문제가 절대 발생하지 않는다는 뜻이 아니다. 현재 관리자 사용자가 제한된 팀원 중심이고, 관리자 기능의 사용 범위와 신뢰 경계가 좁기 때문에 성능 측정의 명확성을 위해 해당 위험을 우선 수용한다는 의미다.

## 3. JWT를 선택한 이유

### 3.1 일반 요청의 DB·Redis 조회 제거

Session이나 매 요청 사용자 조회 방식을 사용하면 인증 요청마다 외부 저장소 접근이 발생한다.

```
요청
 → Session 또는 사용자 정보 조회
 → 사용자·권한 확인
 → 좌석 예약 로직
 → Redis 락
 → 예약 DB 처리
```

이 경우 응답 시간이 증가했을 때 원인이 사용자 조회인지, Redis 락 경합인지, 예약 트랜잭션인지 분리하기 어려워진다.

현재 JWT 방식에서는 Access Token에 다음과 같은 정보를 포함한다.

```json
{
  "sub": "15",
  "type": "ACCESS",
  "role": "USER"
}
```

일반 요청은 다음과 같이 처리된다.

```
JWT 서명·만료 검증
 → userId와 role 추출
 → 좌석 예약 로직
 → Redis 락
 → 예약 DB 처리
```

따라서 인증 단계에서 사용자 DB나 Redis를 조회하지 않으며, 예매 성능을 측정할 때 인증 계층의 추가 부하를 줄일 수 있다.

### 3.2 부하테스트 결과 해석의 명확성

Tiki-Taka에서 주요하게 확인하려는 대상은 인증 자체보다 좌석 예약 처리량, Redis 락 경합, DB 커넥션 사용량, TPS, p95·p99 응답 시간, 동시 예약 성공·실패율이다.

인증 요청마다 사용자 DB나 Session 저장소를 조회하지 않으면, 부하테스트 결과를 예매 로직의 성능과 더 직접적으로 연결할 수 있다. 특히 인증과 예매가 같은 DB 커넥션 풀이나 Redis 자원을 놓고 경쟁하는 상황을 줄일 수 있다.

### 3.3 다중 서버 확장의 단순성

JWT는 서버가 로그인 상태를 별도로 보관하지 않아도 된다. 각 서버가 동일한 서명 키와 검증 규칙을 사용하면 어느 서버로 요청이 전달되더라도 토큰을 독립적으로 검증할 수 있다.

Session도 Redis와 같은 공용 저장소를 사용하면 다중 서버 환경에서 충분히 확장할 수 있다. 다만 매 요청 Session 조회가 추가되고, 해당 저장소의 지연이나 장애가 인증 요청에 영향을 줄 수 있다는 차이가 있다.

## 4. 수용하는 단점과 현재 판단

### 4.1 권한 변경 반영 지연

Access Token에 role을 포함하면 일반 요청에서 DB의 최신 role을 조회하지 않는다. 예를 들어 `ADMIN` 권한으로 발급된 토큰이 아직 만료되지 않은 상태에서 DB의 권한을 `USER`로 변경하면, 기존 토큰은 만료 전까지 `ADMIN`으로 검증될 수 있다.

문서 기준 Access Token의 최대 만료 시간이 1시간이라면, 최악의 경우 권한 변경이 최대 1시간 지연될 수 있다.

이 위험은 현재 관리자 운영 범위에서는 낮게 평가한다. ADMIN 사용자는 프로젝트를 직접 운영하는 팀원 3명을 중심으로 하며, 관리자 계정의 수와 사용 범위가 제한적이다. 따라서 현재 요구사항에서는 대규모 관리자 권한 회수나 role 변경을 실시간으로 처리해야 할 가능성이 높지 않다.

다만 다음을 의미하지는 않는다.

- 기존 ADMIN 토큰이 즉시 무효화된다고 보장하는 것
- 관리자 계정 탈취 위험이 없다고 보는 것
- 권한 변경 지연이 모든 운영 상황에서 안전하다고 단정하는 것

현재의 판단은 제한된 관리자 구성, 팀원 중심의 운영, 현재 기능 범위라는 조건을 전제로 한다.

### 4.2 강제 로그아웃과 토큰 즉시 폐기의 어려움

Session은 서버에서 Session을 삭제하면 다음 요청부터 인증을 차단할 수 있다. 반면 현재 구조는 Access Token 상태를 서버에 저장하지 않으므로, 로그아웃 시 클라이언트가 토큰을 삭제하는 것만으로는 이미 복사되거나 탈취된 토큰을 서버에서 즉시 무효화할 수 없다.

현재 관리자 계정 수가 적고 관리자 기능의 사용 범위가 제한적이기 때문에, 일반 고객 전체를 대상으로 하는 대규모 강제 로그아웃 시나리오의 우선순위는 낮다. 이 단점을 현재 범위에서 수용하되, 관리자 계정 탈취나 즉시 차단 요구가 생기면 같은 판단을 유지하지 않는다.

### 4.3 계정 정지·삭제의 즉시 반영 어려움

일반 요청에서 사용자 DB를 조회하지 않으므로, 계정이 정지되거나 삭제된 뒤에도 기존 Access Token이 서명과 만료 조건을 만족하면 검증될 수 있다. 현재 프로젝트에는 계정 상태를 실시간으로 통제해야 하는 요구가 명확히 포함되어 있지 않지만, 보안 요구사항이 확대되면 별도 무효화 전략이 필요하다.

## 5. 현재 완화 전략

현재의 선택을 무조건적인 JWT 사용으로 확대하지 않기 위해 다음 전략을 적용한다.

### 5.1 Refresh Token 재발급 시 최신 권한 확인

Refresh Token에는 role을 포함하지 않고 userId 중심의 정보를 둔다. Access Token을 재발급할 때는 DB에서 사용자의 존재 여부와 현재 role을 확인한 뒤, 최신 role로 새 Access Token을 발급한다.

```
Refresh Token 요청
 → Refresh Token 검증
 → userId 추출
 → DB에서 현재 사용자와 role 확인
 → 최신 role로 Access Token 재발급
```

따라서 권한 변경이 발생한 경우에도, 다음 Access Token 재발급 시점에는 변경된 권한이 반영된다. 일반 요청의 처리 비용은 낮게 유지하면서 재발급 시점에는 최신 사용자 상태를 확인하는 절충안이다.

### 5.2 관리자 계정의 제한된 운영 범위 유지

현재 ADMIN 계정은 프로젝트를 직접 운영하는 팀원 3명을 중심으로 관리한다. 관리자 계정을 불필요하게 확대하지 않고, 관리자 기능의 접근 주체와 사용 범위를 제한함으로써 오래된 role claim이 악용될 가능성을 현재의 신뢰 경계 안에서 낮게 유지한다.

이는 기술적으로 위험을 제거하는 방법이 아니라, 현재 운영 모델에서 위험의 발생 가능성과 영향을 제한하는 운영상의 완화 전략이다.

### 5.3 Access Token 만료 시간 관리

Access Token의 만료 시간은 너무 길게 설정하지 않는다. 만료 시간을 짧게 설정하면 권한 변경이나 토큰 탈취의 영향 시간을 줄일 수 있지만, 재발급 요청이 늘어나는 비용이 생긴다. 현재의 만료 시간은 성능과 통제 가능성 사이의 균형으로 관리하며, 관리자 운영 범위와 보안 요구사항이 변하면 함께 재조정한다.

## 6. Session을 선택했을 때의 반대 효과

Session 방식은 다음과 같은 운영상 장점을 가진다.

- 권한 변경을 즉시 반영하기 쉬움
- 강제 로그아웃과 특정 Session 삭제가 쉬움
- 계정 정지·삭제를 즉시 인증 실패로 연결하기 쉬움
- 로그인 기기 관리와 동시 로그인 제한을 구현하기 쉬움

대신 일반 요청마다 Session 저장소를 조회해야 하므로 다음 비용이 발생한다.

- Redis 조회 지연과 연결 사용량 증가
- Redis 장애가 인증 장애로 이어질 가능성
- 예매 락과 Session 저장소 사이의 자원 경합 가능성
- 부하테스트 결과에 인증용 Redis 비용이 포함됨

핵심 관계는 다음과 같다.

```
외부 저장소 조회를 줄일수록
 → 요청 처리 독립성과 성능 측정의 명확성은 좋아짐
 → 최신 권한 반영과 즉시 통제는 어려워짐

외부 저장소를 매 요청 조회할수록
 → 최신 상태 반영과 강제 통제는 쉬워짐
 → 요청 비용과 저장소 의존성은 증가함
```

## 7. 재검토 조건

다음 조건 중 하나라도 발생하면 현재의 JWT role claim 결정을 재검토한다.

- 프로젝트 운영에 참여하는 외부 관리자나 다수의 운영자가 추가되는 경우
- 관리자 계정의 수 또는 권한 범위가 크게 확대되는 경우
- 관리자 계정 탈취를 높은 영향도의 위협으로 판단하게 되는 경우
- 관리자 권한 변경을 즉시 반영해야 하는 정책이 생기는 경우
- 관리자 또는 특정 사용자의 강제 로그아웃·즉시 토큰 폐기가 요구되는 경우
- 계정 정지·삭제를 다음 요청부터 즉시 반영해야 하는 경우
- 감사·보안 요구사항으로 최신 사용자 상태를 매 요청 확인해야 하는 경우

이 경우에는 다음 대안을 검토할 수 있다.

- 관리자 요청에 한해 DB 또는 Redis에서 최신 권한 확인
- Redis 기반 권한 캐시
- token version 또는 invalidated-at 기반 토큰 무효화
- Access Token denylist
- 더 짧은 Access Token 만료 시간과 Refresh Token Rotation
- Redis Session 또는 관리자 전용 Session 인증

## 8. 최종 결론

Tiki-Taka는 대량 동시 예매의 성능과 부하테스트 결과의 해석 가능성을 중요하게 보기 때문에, 일반 요청에서 외부 저장소를 조회하지 않는 JWT role claim 방식을 선택한다.

이 선택으로 매 요청 DB·Redis 조회를 줄이고 인증 부하와 예매 부하를 분리할 수 있다. 그 대가로 권한 변경, 강제 로그아웃, 계정 정지, 토큰 탈취에 대한 즉시 통제는 약해진다.

현재 ADMIN 사용자는 불특정 다수의 관리자가 아니라 프로젝트를 직접 운영하는 팀원 3명을 중심으로 하고, 관리자 계정 수와 사용 범위도 제한적이다. 따라서 현재 운영 범위와 신뢰 경계에서는 Access Token의 최대 만료 시간만큼 role 변경이 지연될 수 있는 위험을 수용 가능한 수준으로 판단한다.

다만 이는 문제가 절대 발생하지 않는다는 의미가 아니다. 외부 관리자 확대, 관리자 계정 탈취 위험 증가, 대규모 권한 회수, 즉시 권한 변경 또는 강제 로그아웃 요구가 생기면 운영 조건이 달라지므로 JWT와 Session의 트레이드오프를 다시 평가해야 한다.

> Tiki-Taka에서는 JWT가 Session보다 무조건 우수해서 선택한 것이 아니다. 제한된 팀원 중심의 관리자 운영이라는 현재 조건에서, 대규모 동시 예매 성능을 명확하게 측정하기 위해 일반 요청의 외부 저장소 조회를 줄이는 편익을 선택했다. 권한 변경과 토큰 무효화가 즉시 반영되지 않는 위험은 인지하고 수용하되, 관리자 범위가 확대되거나 즉시 통제가 필요한 요구사항이 생기면 인증 방식을 재검토한다.
